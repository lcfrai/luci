# Windows acceptance handoff

Use the final C082 source checkpoint, including the COPY flag correction. Record its commit, application version, Docker engine/storage driver, available disk and exact reviewed project commit. Use a Linux Docker engine that supports the admitted classic builder and required limits. Prefer an isolated acceptance environment whose selected public base images are already absent; do not prune unrelated images to manufacture a cold state.

1. **Produced application to cold preview.** Create or amend a real application through Discover, Design and Develop, review and commit it, then use Deploy preview. Its ordinary Dockerfile should use an uncached public `FROM` tag or digest. Preparation must not ask the user to run `docker pull`. Observe one admitted pull per unique missing declaration, then a build with pinned image IDs, application start, useful HTTP/UI behavior, and exact Stop. Retain evidence of the app result as well as allocation phases; fixture tests alone do not establish this journey.
2. **Multistage COPY.** Exercise a prior stage alias and numeric index, including a continued COPY instruction. These should build normally. An external, future or current-stage `COPY --from` must be refused before inspection/pull/build. Include quoted or escaped whitespace in a preceding flag: `COPY --chown="0:0 " --from=alpine:3.22 /etc/os-release /out`. The nine-case focused correction regression passed with stable inputs; the correction must be present in the Windows checkpoint.
3. **Authority/source change.** Between a completed pull and the next mutation, revoke Deploy access, reduce relevant policy limits or invalidate the reviewed source through the supported controls. The next pull/build must not dispatch. Already acknowledged work may settle; uncertain work must remain charged. Restore authority explicitly before attempting a new reviewed release.
4. **Cancellation and interrupted acknowledgement.** Cancel before dispatch and confirm no pull/build. In an isolated fault-injection run, interrupt an active pull’s response. The receipt must stay unknown/retained, with no automatic second pull, build or capacity release based only on local image presence. A later explicit Stop must not falsely claim unknown work is settled. Record any missing cancellation/recovery product control as a gap.
5. **No duplicate or unrelated work.** Use repeated FROM references and confirm one pull per unique missing image. Refresh/reopen an unknown release and confirm no replay. A tag retargeted after the pull must not replace the acknowledged immutable manifest/image. No unrelated images should be pulled or tagged. A warm retry under a new authorized release should use observed immutable local bases.
6. **Resource refusal and usability.** Confirm inadequate observed shared capacity, an image above the 2 GiB cold virtual-size policy, or a cold plan above the 32 GiB demand ceiling blocks further build work with an understandable result. Verify the user can distinguish waiting/refused, settled failure and unknown retained work without being told to bypass admission manually.

Capture exact mutation counts/order, release/allocation identity, receipt transitions, resource admission result, app HTTP/UI result and cleanup outcome. Redact real project content, credentials and personal identifiers before sharing. Do not claim success from a container ID or a green unit-test count alone.

Current limits: public pulls have no added registry-credential workflow; dynamic FROM, alternate syntax directives, heredocs and unsupported builder features remain refused. The 15-minute pull/build operation also obeys shorter caller deadlines. Docker daemon downloads/unpacking share a conservative admission allowance rather than a hard per-download quota. Unknown pull settlement is deliberately retained and cannot be inferred from image existence. This change does not itself prove full application compatibility, recoverability or Windows product quality.
