# CLOUD-034: current shared reservation visibility

The owner capacity endpoint previously read its own API process's reservation cache. A team API could persist a check allocation in the shared ledger while the paused owner's repeated GET still showed its earlier totals. This is a global visibility defect, not evidence of an admission bypass. The production admission/mutation implementation (`execution_leases.go`) is byte-identical to the captured original.

The new read-only observer opens the existing private ledger lock, waits cooperatively for at most 100 ms, reads and validates at most 2 MiB through the existing confined reader, and totals all scopes' worker leases and non-finished checks. It creates or repairs no files, changes no permissions, performs no reconciliation or backend operation, and never substitutes stale cache values. The public result is either `status: ready` with successful-read `observedAt` and aggregate `count`, `memoryMiB`, `cpuMillis`, or `status: unavailable` without those fields. Missing, linked, project-owned, oversized, malformed or lock-contended state is unknown. The 100 ms context bounds lock acquisition cooperatively; it cannot preempt synchronous filesystem calls and is not a hard wall-time guarantee. Observed time is a ledger read time, not Docker inventory proof.

`GET /v1/product/swarm-scheduler` retains its existing machine-administrator authorization; team contexts and ordinary members are denied before resource reads. The desktop parser validates the explicit union and numeric/timestamp fields. Legacy, absent or null summaries become unavailable; malformed explicit data rejects the response. The capacity details say **allocations**, include workers and checks across the machine, and expire displayed totals after 30 seconds even if the next request remains pending. No private ownership identifiers are added to the public summary.
