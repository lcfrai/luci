# CLOUD-060 production modal ownership inventory

Read-only inventory and external proposed overlays; no repository edits, tests, builds, browser, Docker or provider workloads were run by this delegate. Base revision for captured owner sources: `db8faad86f2e8e5cbbbe87b8710928c0a5c22a0a`. This is a source review and an uncompiled candidate, not a passing product result.

The source inventory contains **24 production `<WorkflowDialog>` openings in 21 components**. The earlier rapid message's rough 29/22 count was incorrect and is superseded. Imports, tests and the WorkflowDialog definition are excluded. WorkflowDialog's intended `readAccess` contract is `{canRead:boolean; loading:boolean; error:string}`. Render private modal contents only when all of `canRead`, `!loading`, `!error`, and workspace display admission hold. `canRead` alone deliberately retains historical read access during refresh/error and is insufficient.

All admission owners below run **above** the Activity owned by WorkflowDialog. Never move these hooks into the modal's suspended payload: an effect that must obtain fresh authority cannot be suspended by its own missing authority. Project IDs must be the private data's exact owner, never an unrelated global selection or a pending navigation destination. This is display admission, not an execution/mutation grant.

## Bulk cancellation details and required checks

- Selection stays in ScopedOverview; the new owner only projects permission. Suspending it does not invoke apply, onClose, onSelect or onForget.
- Deduplicate and sort only IDs used for permission keying. Preserve selected task order and exact row objects displayed/applied.
- Validate response `team.id` and `projectId`; a wrong owner or any read refusal fails closed for the **whole selected review**, rather than rendering a partially private list.
- Do not infer read access from historical `Picked.canExecute`, current selected project, another project's positive permission, successful old queue read, or team-level `read` alone.
- Four-reader concurrency is bounded per current batch; aborted results neither publish nor enqueue another lookup. Server-side request preemption is not claimed.
- Existing apply still requests current exact project permissions sequentially and keeps existing partial-failure/uncertainty/CAS semantics.
- Test A allowed/B denied with B selected and global selection A; loading/error with prior selected names; restore exact both IDs; change selected project set while a prior batch is held; aborted late positive; wrong project/team response; busy close/cancel disabled; no cancellation route called by suspend/restore/revalidation. Also count maximum outstanding current-batch permission reads.

## Unresolved policy / privacy boundaries

1. **DraftNavigationDialog denied-source navigation.** The candidate hides private labels under exact source-project suspension. If granular source access never returns, the generic fallback Close review can only cancel navigation; it does not expose the existing keep/discard choices. Consider safe `unavailableContent` offering the same explicit local keep/discard actions with generic wording, without draft labels/content or granting server read. This is preferable to allowing stale private labels or stranding navigation. Workspace-switch has a separate public generic decision already.
2. **TeamPanel mixed workspace/project authority.** Whole-workspace deny now suspends its portal, but an already-open TeamPanel caches `detail` and `projectAccess` across `workspace.revision`. Using detail.permissions alone for project-sharing/member edit UI can preserve stale privilege presentation during a granular role change. Do not expand C060 into a redesign silently. Minimum scoped follow-up: keep workspace/member read ownership distinct; use current workspace permissions for admin action gating; revalidate exact sharing project on revision and gate only that project-sharing section via an outside-Activity owner. A project hook selected by sharing target is legitimate; gating the entire team/billing modal by unrelated selected project is not. No runtime defect was executed here.
3. **All ordinary authority hooks remain above Activity.** Suspension cleans nested modal effects but should not clean parent mutation ownership, answer-draft registration, recovery review idempotency map or permission-refresh effect. Parent close handlers may be busy/dirty guards; never invoke them to force disappearance.
4. **Focus paths.** Core must handle both Radix onCloseAutoFocus and useDismissable cleanup, suppressing return into hidden/inert workspace. A generic inline close is not a replacement for removing modal aria-hiding, pointer-events, scroll lock and focus traps.
