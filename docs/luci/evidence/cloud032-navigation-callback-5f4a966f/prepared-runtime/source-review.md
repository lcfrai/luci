# Bounded project-switch source assessment at5f4

The prior edd0 full432-row await analysis located large inclusive All-projects click, Open click, heading-wait and evaluate intervals. Its data did not attribute those intervals to React. The settled32-call control later observed Locator median10.594ms versus retained-handle2.217ms, with0.100ms median callback durations, on a different settled protocol. These historical observations remain separate and are not subtracted from the new original-action measurements.

Actual source work along the current path:

- `store/slices/uiSlice.ts`: `selectProject` checks available projects and unsaved drafts, then synchronously computes `navigationState`. `navigationState` calls `writeProjectNavigation` before publishing selection. `preferences/projectNavigation.ts` sorts/bounds retained positions, JSON-serializes the small navigation preference, enumerates localStorage keys to evict only old navigation scopes and calls synchronous setItem. The Zustand store also persists its deliberately selected preference fields via createJSONStorage. These are concrete synchronous operations in the click path; neither stored size nor their elapsed cost was instrumented in the old receipts. The source's64-project/eight-scope bounds and fresh four-project fixture do not justify claiming this is the tail cause or removing persistence.
- `components/AppShell.tsx`: selection subscriptions switch between ProjectsHome and a LensRouter keyed by project/source revision; Orchestrator is a sibling subtree. Project switches therefore unmount/mount relevant UI and run their effects. The source contains no serial await of Orchestrator before Definition.
- `components/projects/ProjectsHome.tsx`: name filtering and the overview board render from the project catalogue. `ProjectOverviewBoard.tsx` launches at most four concurrent overview reads; each completed read merges one summary state and can rerender the visible board. It separately mounts HostCapacity. Its primary Open project destinations precede asynchronous content and directly select the project, so the source does not impose an overview-response barrier on navigation. Read cleanup aborts on unmount;15s refreshes do not overlap. Summary work is concurrent and potentially relevant to render cost, but old response-delivery experiments did not establish it as the cause.
- `components/projects/HostCapacity.tsx`: an authorized host-capacity GET independently updates its local state; a15s visibility-aware refresh and freshness timer exist. Those are separate reads, not a prerequisite for the Open project button.
- `components/definition/DefinitionWorkspace.tsx`: one generation/permission/cancellation-fenced specification read commits saved spec, base and ready state. Its controlled The idea field follows the spec's purpose. The exact-value callback can therefore wait for this read/commit, but the source cannot tell whether it did in any historical long row.
- `components/orchestrator/OrchestratorPanel.tsx`: its independent refresh and10s idle/2.5s active-job polling can create concurrent local rendering. Turn merging/sorting is render work. The fresh paused/no-provider fixture and old timing receipts do not establish large turn collections or a bottleneck in this branch.
- `hooks/useProjectDraft.ts`: clean-editor persistence returns without serialization/write. Draft recovery reads occur at mount; dirty input persistence is a separate path. Removing recovery or weakening unsaved-edit guards would change behavior without evidence that clean switching time is caused there.
- `components/teams/TeamWorkspaceProvider.tsx`: authority/context is explicit and memoized, personal access and team refresh have distinct paths. The callback adds no new authority claim; source review must not infer an access refresh occurred merely because one is possible.

No avoidable serial response barrier or concrete latency defect is proved by these reads. The approved callback timing is the next specific discriminator: first-sample immediate match versus counted disconnection/value waiting, with entry and match ordering compared to the independently sampled readiness witness. That can narrow app-ready versus automation observation delay without asserting physical paint, continuous readiness or an internal app root cause. No speculative production patch is staged.
