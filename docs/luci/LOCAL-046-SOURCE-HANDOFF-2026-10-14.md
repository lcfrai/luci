# LOCAL-046 OpenCode conversation source handoff — 14 October 2026

The local Windows tester observed an OpenCode 1.18.34/Ollama conversation with a 1 GiB Docker limit, no Docker OOM and 738 generated tokens. The launcher exited 2: OpenCode's `--file` path treated `prompt.txt` as a text attachment and the returned analysis echoed its line-truncated source context, missing the current request near the end of a 3,141-character serialized line. Existing strict result validation correctly refused that output; no reply was accepted.

Pinned upstream source: `sst/opencode` tag `v1.18.34`, commit `aec0b9a6d8898f68f923aaf08b7306d931fd9d76`, `packages/opencode/src/cli/cmd/run.ts` at its stdin input (`Bun.stdin.text()` and `resolveRunInput`) and session prompt construction. Its piped stdin is the message text; `--file` creates a separate file part. Luci's read-only `luci-analysis` agent, exact configured model and bounded JSON event parser remain in place.

The launcher now sends a bounded text message containing the complete prompt and the exact generated response schema over stdin, with no file attachment. This preserves the current request after a long context line and tells the selected harness to return only one schema-matching JSON object. The API still rejects unknown fields, malformed/fenced output, stale proposal identity and unreviewed work; this path does not grant tools or infer success from provider text.

The first installed retest confirmed full stdin delivery but found an independent serving-window truncation. Ollama logged a 6,178-token prompt against a 4,096-token serving context with roughly 2,048 tokens reserved for output. The saved model's training context is larger, but it does not change the actual server window. A byte cap alone cannot prove token fit, and a 512-token output budget cannot cover a normal complete specification proposal.

The read-only OpenCode analysis route now provides `limit.context=8192` and `limit.output=2048` for a local Ollama endpoint. A short custom analysis agent prompt replaces OpenCode's large default coding prompt; pinned upstream `session/llm/request.ts` selects `agent.prompt` in place of `SystemPrompt.provider`. The identical exact response schema is transmitted compactly: the orchestrator contract is 5,950 bytes instead of 20,061 after Python indentation. Before OpenCode generation, the launcher sends the full prompt to the exact selected model via Ollama `/api/generate` with `raw:true`, `stream:false` and `num_predict:1`. This is a bounded model call, not a free tokenizer lookup. Its `prompt_eval_count` reports evaluated input tokens; pinned Ollama `runner/ollamarunner/runner.go` truncates oversize input to the serving limit, which saturates this count near that limit. Luci checks `/api/ps` for the loaded model's actual `context_length` and digest. It requires at least 8,192 serving tokens and evaluated input + 2,048 output + 2,048 system/template allowance to fit the **smaller** of that loaded window and OpenCode's declared 8,192-token context. A final read-back rejects a changed loaded context/digest. The 14,000-byte limit is only a transport/memory bound; it is not treated as a token estimate. The existing-model alias [setup recipe](LOCAL-MODEL-CONTEXT-SETUP-2026-10-14.md) avoids a model download or global setting. Actual resource admission and host monitoring remain unchanged. It does not change OpenCode coding-session limits.

Focused Python-backed Go tests cover the long context line and tail request, equivalent parsed schema delivery, fenced-output refusal, actual served-window/count acceptance, refusal of a 4,096-token window, refusal of high-token text below the byte cap even when Ollama loads a larger window, and pre-launch oversize refusal. Distinct `local_model_context_limit` and `local_model_context_unverified` failures are retained without raw provider output. These source checks do not establish actual model quality or provider compatibility with the raw-generation preflight. The Windows tester should configure the source-bound 8k alias, verify the same Orchard conversation with exact effective Docker memory/CPU, loaded model digest/window and prompt evaluation, then inspect a complete accepted response/proposal or a truthful failure. Installed result quality and host memory remain open.

The later 8k Orchard retest confirmed actual input within the served window (`n_tokens=3173`, `truncated=0`) and normal HTTP completion, but the model itself returned an incomplete 239-byte object with `proposal:null` and `nextAction:"Propose ..."`. The previous product-definition instruction called a full proposal optional even when the person explicitly requested one; it now requires a complete draft when context suffices and asks one real question when a material decision is missing. OpenCode's pinned `run.ts` uses `--format json` only for event framing; it does not forward a response format to `session.prompt`. Pinned `session/prompt.ts` supports `format:{type:"json_schema",schema,...}` through its dedicated StructuredOutput tool and returns the validated object as `info.structured` from the session message route. The local Ollama branch therefore starts one authenticated loopback `opencode serve` child in its owned sandbox, posts the full text and exact schema to one private session, and accepts only its bounded structured object after another loaded-model identity check. The child is retired at terminal outcome. Missing required fields, a deferred `proposal:null` when the selected answer says to propose, changed model identity, or unknown output still fail closed; neither a provider text fragment nor a tool claim grants project authority. Nonlocal OpenCode, Codex, Claude and coding-session routes remain unchanged.

Focused source fixtures exercise the exact long Orchard-style tail/schema transport, private server authentication, missing fields, semantic proposal deferral and valid structured response. The installed model's actual ability to produce a complete proposal under the finite token/resource budget remains to be retested; no real-model or product acceptance is inferred from these fixtures.

Pinned OpenCode `v1.18.34` control-flow review found an additional requirement for that retest. `session/prompt.ts` injects `StructuredOutput` at lines 1243–1250 after resolving ordinary tools, then `session/llm/request.ts` lines 210–215 filters **all** tools through `Permission.disabled`; `permission/index.ts` lines 204–213 chooses the last matching rule. A blanket `{"*":"deny"}` therefore removed the dedicated output tool even though the fake HTTP server fixture returned `info.structured`. The analysis configuration now appends an exact `StructuredOutput:allow` exception while retaining `*:deny`; its prompt permits that output-only tool and still forbids coding, filesystem, shell, network and MCP tools. OpenCode's `createStructuredOutputTool` executes schema validation and captures the answer; it has no filesystem or external effect. Source configuration and fixture checks pass, but only an installed run can establish that the selected local model actually calls the tool and produces the full draft.
