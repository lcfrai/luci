## What can be reused and what cannot yet be claimed

Luci already has exact task/context input, upstream Codex/Claude Code/OpenCode harness contracts, dependency scheduling, guarded candidate review, deployment gates and an E2B Embed controller with retained Create/Delete uncertainty, result capture and restored-identity reconciliation. The current `control-plane/internal/backend/e2bbe` deployment validation accepts AWS `m8i` host types; `control-plane/cmd/api/e2b_config.go` loads its private operator contract. This source does **not** select an Azure deployment or prove that the guest, template, network and off-host store work on Azure. Keep the existing adapter and upstream coding engines where their contracts fit; do not implement a new coding engine or substitute SSH Docker for microVM Develop.

The pinned [E2B runtime Azure Embed recipe](https://github.com/e2b-dev/runtime/blob/cf536c284434fdd2f09bbab35ec807a5dacc87e4/embed/terraform/azure/README.md) creates one Ubuntu 24.04 VM Scale Set instance intended to run Firecracker guests. That host is an Azure VM; **each Luci task subagent must instead own a separate newly created E2B/Firecracker microVM on it**. One Azure VM running four task containers would fail LC-06/15. The upstream default `Standard_D4ds_v7` is four vCPUs/16 GiB and reserves 4 GiB hugepages; it is a reference starting point, not proof that four concurrent Luci guests fit. Microsoft's [Dv5 size documentation](https://github.com/MicrosoftDocs/azure-compute-docs/blob/38164b4abefebfaac6966d71eec8c36c781b7bf9/articles/virtual-machines/sizes/general-purpose/dv5-series.md) identifies nested virtualization for a candidate family. Region, offer, zone, exact SKU, available quota, actual guest `/dev/kvm`, template capacity and cost require later authorized verification. Offline code must accept a validated configured host identity and measured capacity rather than bake in a subscription or SKU. The representative target is **12 dependency-aware tasks across four projects, four distinct concurrently owned microVMs**; four is a test configuration, not a product ceiling.

## Chosen offline integration boundary

1. **Fixed private TLS gateway.** Run Envoy on the E2B Embed host, listening only on its private Azure VNet interface; the separately hosted Luci controller reaches it through private DNS. Envoy requires a controller client certificate, validates its trust root and exact identity, terminates TLS, and forwards only allowlisted E2B API/admin and verified guest-origin routes to **loopback-only** runtime listeners. Host firewall and Azure network rules block direct port 5008 and runtime guest ports from every remote peer; a private VNet by itself is insufficient. E2B's separate `X-API-Key` and `X-Admin-Token` remain mandatory authorization at the runtime. Do not expose a public dashboard or an open dynamic forward proxy. Extend the existing `privateHTTP`/guest transport to load a separate private client certificate/key and pin the gateway CA/server identity; current code has server TLS validation and private-address checks but **no client-certificate authentication**. This is a concrete offline code task, not a claim that a gateway is deployed. [Envoy's pinned mTLS guide](https://github.com/envoyproxy/envoy/blob/2eff6e8ccfcf7ed5ac2de5880499995ea29f8648/docs/root/start/quick-start/securing.rst) documents downstream client-certificate validation. Route and certificate rotation must fail closed on an unknown sandbox ID or lost gateway response; uncertain provider mutations retain their exact journal entries.
2. **Identity and secret delivery.** Use distinct user-assigned managed identities for the Luci controller and the E2B host. Use the official Azure Go `azidentity` managed-identity credential and Key Vault `azsecrets` client; grant the controller identity read access only to its scoped E2B task/admin and mTLS secrets, and the host identity only to runtime bootstrap secrets. Materialize those values at service startup into private, owner-only, ephemeral files consumed by the existing absolute-file operator config; rotate by controlled service/gateway generation, never silently replace a key while a mutation is uncertain. Do not place secrets in Terraform state, VMSS custom data, source, task archives, browser or guest metadata. The selected upstream model credential follows Luci's existing task-scoped secret route and exact egress allowlist. Implement strict private-file lifecycle and cert/key validation; if managed identity, Key Vault or credential read is unavailable, new cloud effects refuse while retained ownership remains observable/recoverable. Key Vault/identity access is a deployment prerequisite, not needed to compile this boundary offline.
3. **Separate durable controller disk.** Run the Luci controller on a different Linux host from the replaceable E2B VMSS instance. Put `controllerStateDir`, `DirectoryStore.Directory`, execution ledger, product state, transfer artifacts and staging under one dedicated, encrypted, single-writer Azure managed data disk mounted as a local POSIX filesystem (ext4 selected for the first implementation). Do not put authoritative data on the VMSS OS disk, an unverified network mount or a Blob FUSE path. Existing `DirectoryStore.writeAtomic` writes and fsyncs a temporary file, renames it and syncs the directory; `commit` verifies the immutable journal before moving `head.json`, and `statelease` guards a live writer. Offline wiring must verify the mounted disk/resource identity, filesystem, private paths and host separation before it enables Create. Backup/snapshot copies are separate disaster recovery evidence and may lag the last acknowledged head; they cannot silently reconstruct a lost commit.
4. **Host-loss protocol.** Stop admission when the controller or Embed generation changes. Revoke/fence the old controller gateway certificate and verify the old controller has stopped or lost the single-writer disk attachment **before** mounting that disk on a replacement; a filesystem lock alone cannot fence a still-running host. Refuse split brain or an unverified restore head. Open exact state and artifacts, compare current `head.json`/journal digest and transfer hashes, then use `DirectoryStore.RestoreController` and `ReconcileRestored` for every retained VM before dispatch. Read exact provider IDs and host generation, retain unknown Create/Start/Delete and their reservations, and never allocate a replacement from a timeout. If restoring only a backup whose acknowledged head cannot be proved, keep the scope recovery-blocked for explicit reconciliation; do not imply RPO-zero from snapshot existence. Rebuild/pin runtime templates on the new VMSS host from verified source before any new task. Existing record/receipt fields support part of this flow; Azure disk identity, generation fencing and restore admission are remaining code.
5. **Azure deployment identity.** Keep the E2B API and task ownership model, but add an explicitly named `deployment.provider="azure"` contract, rather than accepting AWS `m8i` under an Azure label. The private operator configuration records stable Luci scope, Azure subscription/resource-group/VMSS resource IDs, selected region/SKU/zone, exact VMSS instance/boot generation, independently hosted controller disk resource ID, authenticated gateway identity/receipt, runtime/template build identity, store-separation/restore receipt and host node ID. None is inferred from a URL or provider response. Resource IDs and nonsecret receipts stay out of task input and are bound to the journal; secrets remain separate files. `control-plane/internal/backend/e2bbe/controller.go:newController` currently requires `provider=="aws"`, so it needs strict Azure-specific validation and identity mismatch refusal. `control-plane/cmd/api/e2b_config.go` must parse/bind the Azure fields, verify the protected origins and durable mount, and keep AWS as a separate capability. `cloud_swarm_dispatch.go`, `cloud_swarm_observe.go`, scheduler and primary recovery UI must carry the selected provider identity without bypassing current authority, source, spending, result-review or no-replay guards.

These are **design choices for the offline implementation**, subject to the originating local architecture audit. They do not claim the selected Azure resources exist, that Envoy or Key Vault is installed, or that the current source already implements Azure.

## Behavioral invariants retained by Azure wiring

| Boundary | Required design and observable refusal |
| --- | --- |
| Host and management | The selected private Envoy gateway must pin both sides, require controller client identity, preserve separate E2B task/admin auth, refuse redirects, bound requests and retain mutation uncertainty. E2B's internal port 5008 is unauthenticated and must never be directly reachable from user/public networks. The upstream Terraform opens client ports 3000–3002, uses public IPs, and is **not** a production Luci deployment as written. Refuse Azure selection until protected management and guest origins are verified. |
| Identity and secrets | Separate Luci actor/team authority, Azure controller/host managed identities, E2B admin/team keys, guest attach key and the selected upstream model credential. Key Vault is the chosen Azure secret source, but it is **not implemented or configured yet**. Deliver only a task-scoped model credential to a verified guest with restricted egress. Do not copy host CLI auth stores or upstream Terraform-state/custom-data secrets. The upstream dashboard cookie is not Secure over HTTP; do not expose that dashboard to users. |
| Context, harness and result | Build an immutable, bounded task input from the accepted context revision, source digest, dependency proofs, task/attempt identity and current grants. Transfer verified bytes to a fresh microVM; keep approved context read-only to the coding user. Run an existing upstream harness through the current sandboxd/attach contract. Capture exact exit, changed files, checks and output into the independently durable store before reviewed integration or VM retirement. A model's success claim alone cannot authorize merge, checks or Deploy. |
| Persistence and host loss | Use the selected separate controller and single-writer ext4 managed data disk for the authoritative journal/artifacts. Upstream explicitly says VMSS replacement starts with fresh storage and loses templates. Pin and rebuild signed templates on replacement; a Blob config object or backup snapshot is not a task checkpoint. Restore exact reservations and owned provider IDs, read back provider state **before** new dispatch, and retain unknown Create/Start/Delete without replay. |
| Ownership, capacity and cost | Give every task one durable Luci attempt ID, exact E2B VM ID, host generation and allocation/estimated-spend record. Enforce current actor/team authorization and configured concurrent CPU/memory/spend policy at effect time; backpressure under actual host and provider limits. On finish/cancel/failure, capture outputs, request exact owned VM stop/delete, prove absence and only then release Luci's active reservation. Keep unknown identity/transport/absence and retained charges visible in the primary conversation. Luci reservation, observed provider usage and final Azure invoice are three distinct facts; the pinned Embed API supplies no final invoice receipt. Deallocated Azure host compute may stop billing while disks/network persist. Never report final cost settlement from VM absence alone. |
| Deploy and teams | Develop environment is separate from the app deployment target. Reviewed candidate, independent checks, release authority, health and rollback must continue through the existing product routes. Accepted teammate amendments update exact shared context; stale attempts are stopped or reconciled without disturbing unaffected projects. A contradictory human intent stays unresolved until an authorized decision. |

## Offline code plan and deployment/run gates

After local architecture audit and local readiness, **cloud Sol is the sole implementation owner** for the Azure config/parser, gateway client identity, deployment validation, data-disk/store guards, restored identity reconciliation, scheduler/result/retirement joins and primary recovery display. The local Sol worker owns later isolated source/Windows verification; local Astra owns acceptance orchestration and the issue ledger. No worker is delegated from this session. The implementation may use fake provider, gateway, Key Vault and mounted-disk fixtures to check refusal and recovery paths without an Azure account. Keep all AWS original source/fixtures, LC-01–LC-16 behavior and existing local Docker capability intact.

| Code step after audit | Exact affected entry points and required result |
| --- | --- |
| Azure selection | `control-plane/internal/backend/e2bbe/types.go` and `controller.go:newController`; `control-plane/cmd/api/e2b_config.go`. Validate Azure resource IDs, region/SKU/zone and host generation as configured values, pin management/restore receipts, reject AWS/Azure mismatch and unknown fields, and surface an explicit unsupported/unconfigured state. No subscription query is needed to implement parsers. |
| Protected transport and secrets | `e2bbe/client.go:privateHTTP`, guest transport and `cmd/api/e2b_config.go` add owner-only client cert/key file inputs, gateway CA/identity checks and no-public-address routing. Add a narrowly scoped Key Vault materialization interface for controller/host managed identities, private ephemeral files and rotation; fail closed on missing credential or gateway. E2B task/admin headers remain separate. |
| Durable controller and restore | `e2bbe/store.go:DirectoryStore`, `RestoreController`, `controller.go:ReconcileRestored`, `cmd/api/e2b_config.go:openE2BTaskRuntime` and execution ledger startup bind the configured data-disk resource/mount and writer generation. Refuse data on the VMSS host or wrong disk/snapshot head; prohibit new Create/Start until exact retained IDs are reconciled. Retain ambiguous allocations and original evidence. |
| Task swarm and return | `internal/api/cloud_swarm_dispatch.go`, `cloud_swarm_observe.go`, `internal/product/project_swarm_scheduler.go`, candidate/check/release routes and the primary cloud recovery UI carry Azure attempt/host identity through one VM per task, immutable result, reviewed integration, stop/absence and retained-charge state. Existing authority, task/context/source, policy and no-replay guards remain effect-time gates. |

The **later deployment/run gates**, rather than offline code prerequisites, are: an approved Azure subscription and spending boundary; selected region/zone and SKU available to that offer; [regional/family vCPU quota](https://github.com/MicrosoftDocs/azure-compute-docs/blob/38164b4abefebfaac6966d71eec8c36c781b7bf9/articles/virtual-machines/quotas.md), actual capacity and measured `/dev/kvm`; protected VNet/DNS/TLS gateway and granted managed identities/Key Vault; independently hosted [managed data disk](https://github.com/MicrosoftDocs/azure-compute-docs/blob/38164b4abefebfaac6966d71eec8c36c781b7bf9/articles/virtual-machines/managed-disks-overview.md) with verified mount, backup, restore and signed templates; current model connection and cost policy. Check actual account permissions before provisioning. [Azure compute billing states](https://github.com/MicrosoftDocs/azure-compute-docs/blob/38164b4abefebfaac6966d71eec8c36c781b7bf9/articles/virtual-machines/states-billing.md) distinguish stopped allocated from deallocated hosts; persistent storage/network, model use and final invoice need separate evidence. No price or invoice is inferred here.

Only after those gates and established authority should one real upstream-harness microVM task run, followed by the 12/4/4 workload with mid-swarm amendment, conflicting outputs, independent review/check/Deploy, lost Create, cancellation, restart and host loss. Record distinct concurrent VM identities, exact output binding, stop/absence, retained charges and later billing evidence if an authenticated feed exists. Fixture/source checks do not pass these gates. AWS remains the later provider.
