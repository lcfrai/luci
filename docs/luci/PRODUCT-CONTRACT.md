1. **One primary conversational Luci per person.** This is the main interface and continuing coordinator across projects and the whole lifecycle. It remembers that person's intent and authorized project state, asks about consequential ambiguity, explains what is being built and what happens next, and acts within agreed policy. A saved project chat or a button opening discussion alone does not satisfy this. Per-person identity does not require a permanently running expensive worker for every person/project.
2. **Discover, Design, Develop, Deploy are four communicating, revisitable views of that workflow.** Discover and Design develop exceptionally useful structured context: outcomes, users, decisions, constraints, behavior/design, dependencies and measurable acceptance. Develop boots and orchestrates existing supported upstream Codex, Claude Code or other coding harnesses. Deploy gets the resulting application live and supports operation and amendments. Direct editors, terminals and review tools remain available within the coordinator's coherent journey.
3. **The execution boundaries are explicit.** Local Develop uses isolated Docker; cloud Develop uses isolated microVMs on a specifically supported provider. Luci owns context, environment lifecycle, coordination, review and delivery; upstream harnesses own coding engines. Remote SSH Docker and dormant Kata do not fulfill cloud microVM execution. Management services, image preparation and deployed applications may use Docker without changing this distinction. Show **Run on** separately from **Deploy to**.
4. **A mid-build request drives the complete amendment loop.** Luci performs necessary discovery/clarification and design, versions and reviews affected context under policy, plans affected work, invokes the chosen upstream harness, observes independent checks, reviews/integrates source, updates preview and actually deploys when configured authority/cost/release policy permits. Explain a genuine policy/access blocker without inventing success. Routine allowed steps proceed without humans carrying handoffs between screens. Draft-only changes, manual export/import, preview alone and a plan for later execution do not complete this requirement.
5. **Each teammate's Luci coordinates against authoritative shared project state.** Persist accepted revisions/events, actor identity, intent, ownership, dependencies and causal links. Broadcast accepted changes; reconcile compatible concurrent intent under established policy; invalidate stale evidence and rebase/replan only affected work; continue affected implementation, checks, review and deployment under policy. Contradictory human intent is an explicit unresolved decision, not invented consensus. No silent last-writer-wins, message-only agreement, blanket restarts or requirement that humans manually coordinate routine handoffs.
6. **Keep quality and operational requirements.** Four or more projects advance fairly with priorities and strict context/source isolation. Preserve reviewed outputs, pause/cancel/retry and restart recovery, bounded RAM/CPU/disk/provider demand, exact ownership and truthful provenance. Deliver fast, accessible, consistent shadcn/ui controls and usable global attention/actions. Keep the unchanged measured gates (project-switch p95 below300ms, input p95 below100ms, interaction p99 below1second) and retained failures. Selectively reuse Glasses-discovered/open-source solutions with licence and capability evidence; do not build a replacement coding engine or custom hypervisor without a demonstrated need.
7. **Elastic cloud swarms are first-class, CLOUD-088.** The primary Luci makes it easy to decompose a goal into many smaller dependency-aware tasks and fan out multiple upstream-harness subagents. **Each task subagent gets its own newly allocated isolated microVM**, then its owned VM spins down on completion/cancellation/failure according to exact settlement/recovery policy. A shared VM with multiple processes/containers does not pass. Expose accessible concurrency, resource and spending policies in the normal conversational workflow; dynamically schedule/back off under actual provider/global/per-project limits, without a fixed tiny product ceiling or an unlimited-capacity promise. Preserve task-local context versions, durable artifacts/checkpoints, amendment propagation and reviewed conflicting-result integration. Bound retries, protect against duplicate Create after lost responses, recover across restart/cancel, and make every retained VM/charge and uncertainty visible until settled.

Open-source self-hosting and optional paid managed team workspaces remain the longer-term delivery model. Local-first is sequencing, not removal of cloud microVM, team coordination or actual deployment from the contract. Fixed team subscription plus separately billed model/infrastructure costs remains the selected commercial direction. Cloud-only access/billing must not stop independent local work after the gate is lifted.

## Architecture and trust boundaries

This is the target architecture; the capability map below identifies missing pieces.

| Layer | Responsibility and durable contract |
| --- | --- |
| Per-person Luci | Authenticated conversational identity, private intent and durable continuation, explicit selected project/account, visible progress/decisions and policy-bounded actions. Share authorized project changes, not another person's private credentials or unrelated context. |
| Shared project authority | Canonical versioned specification/design/tasks/decisions, approvals, source identities and causal intent/event records. Atomic compare-and-swap, current grants and accepted-version publication determine truth; messages do not. Scoped event replay and receipts survive restart/compaction. |
| Coordination and planning | Decompose accepted intent, discover affected dependencies, retain contradictions and choose bounded compatible reconciliation. Invalidate affected evidence; preserve immutable original assignments and unrelated running work. Schedule continuation with explicit operation identities and no duplicate side effects after retries. |
| Policy and scheduling | Current Read/Edit/Execute/Secrets/Deploy authority plus configured review, model, deployment and cost policy at each mutation. Routine actions may be preauthorized; a new click is not required for every allowed step. New authority/spend is never inferred. Global and per-project capacity/fairness account for all owned processes and retained uncertain allocations. |
| Upstream execution | Docker locally; a real supported microVM backend in cloud. Transfer only exact approved task/source/context, use existing native CLI adapters, manage credentials through supported scoped connections, and observe actual exit/output. Record provider, harness/version, environment and operation identities. |
| Verification and delivery | Returned claims remain separate from independent checks. Reviewed integration binds exact source/context, then preview and actual deployment/health receipts bind that source and intended target. Maintain and amend the deployed application; do not treat a sandbox URL or local preview as production delivery. |

The coordination service must invoke existing typed admission/execution/review/release operations rather than create a parallel coding engine or weaker duplicate gates. Current per-project conversation storage is a foundation, not already the per-person/shared-team architecture. Proposed policy/coordination endpoints are not shipped API merely because draft code exists.

Keep four identities distinct: (a) a person's primary Luci, (b) another teammate's primary Luci, (c) a task-specific upstream subagent, and (d) that task attempt's owned microVM allocation. One person can coordinate many projects/tasks without launching one heavyweight process per conversation. A task's retry may require a new attempt/VM only after the previous attempt's ownership is settled or explicitly retained/charged; reconnecting to the same live attempt must not replay its command. Capture bounded durable results/checkpoints before teardown. Compute disappearance, retained disk/snapshot charges and provider billing observations are separate facts; spin-down alone is not a zero-bill claim.
