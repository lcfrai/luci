# CLOUD-024: preserve later check outcomes during completion observation

On 8 October 2026, review found that an earlier finished check receipt could overwrite a later command's durable outcome. The observer protected a later command only while its execution lease still existed. After that lease was acknowledged, observing the earlier receipt called `RecordProjectCheckObservation`, which marked later commands skipped. The same defect occurred when the later command was blocked during preparation and never acquired a lease.

The controlled regression used the real HTTP/product/private-ledger path with the existing deterministic backend adapter. Only the final completion ACK was interrupted. Reverse receipt order used the observer's normal cursor, starting at position 1; this represents a valid retained pagination position after a prior page of live jobs. The blocked-preparation case reproduced without reversed order or a later lease.

The correction checks the later saved command outcomes as well as later retained leases before publishing an earlier finished receipt. An earlier receipt whose exact result already matches may be acknowledged without changing the later outcome, run status, held flag or recovery work list. Queued/running command progress alone is not a completed outcome. An interrupted controller that published second-command progress but never admitted that command still becomes an incomplete unknown run with that unstarted command skipped; observation never starts it.

Only `control-plane/internal/api/check_observation.go` and the new `project_check_observation_order_test.go` changed. Product runtime, authority, scope, identity, resource charging and Docker RPC code were unchanged. Source application verified the original bytes before copying and the applied bytes against the tested overlay afterward. [source-manifest.json](source-manifest.json) records both hashes and the integrated checkout's historical base HEAD; that HEAD alone does not represent its pending integrated changes.

The final five cases cover passed, failed, blocked before reservation, later cleanup still pending, and an unknown interrupted run whose later command remained running in the public row without an execution lease. They retain exact command output/exit/status, verify the unsettled later lease remains unchanged, and assert observation makes no backend calls. The final case was added after preserving the original reproduction; both exact test versions are included. The HTTP contract golden emitted by the affected run matched the current fixture byte for byte.

Each run records its exact command, unmodified stdout JSON events, stderr, overlay mapping, and before/after hashes of 718 control-plane/tool-workspace inputs plus its overlay source inputs. These snapshots deliberately cover this control-plane selection, not the earlier broader sandboxd source manifest. Both runs used the pinned Go 1.26.3 toolchain, `GOMAXPROCS=2`, `-race`, `-p 1`, and `-count 1`; captured inputs remained unchanged during each run. [SHA256SUMS](SHA256SUMS) binds the retained artifacts. The external runner and original absolute overlay paths are preserved for provenance; the source bodies needed to reconstruct those overlays are included here.

This is a controlled application/ledger regression witness. No Docker, browser, native Windows, installed artifact or real-model execution was performed. No full-suite rerun was claimed. Independent source review also confirmed that the pinned Docker v28.3.3 `Info` fields `CpuCfsPeriod`, `CpuCfsQuota`, and `PidsLimit` match the new capability checks: both CPU flags expose the daemon's CFS support used by `NanoCpus`, while the daemon can otherwise discard an unsupported PID ceiling. Actual installed enforcement remains a separate runtime gate.
