# Azure microVM Develop: architecture proposal for local audit

**Status: proposal only, 14 October 2026 (Australia/Brisbane).** Local Docker functionality and Windows acceptance come first. The originating local reviewer must audit this architecture before Azure feature code begins. Nothing here authorizes Azure resources, spending, account changes, public endpoints or cloud execution. The [canonical LC-01–LC-16 contract](PRODUCT-CONTRACT-LC.json) and [provider order](PROVIDER-ORDER-AMENDMENT-2026-10-14.md) are unchanged. The existing AWS-specific E2B source and evidence remain historical, not Azure support.

## What can be reused and what cannot yet be claimed

Luci already has exact task/context input, upstream Codex/Claude Code/OpenCode harness contracts, dependency scheduling, guarded candidate review, deployment gates and an E2B Embed controller with retained Create/Delete uncertainty, result capture and restored-identity reconciliation. The current `control-plane/internal/backend/e2bbe` deployment validation accepts AWS `m8i` host types; `control-plane/cmd/api/e2b_config.go` loads its private operator contract. This source does **not** select an Azure deployment or prove that the guest, template, network and off-host store work on Azure. Keep the existing adapter and upstream coding engines where their contracts fit; do not implement a new coding engine or substitute SSH Docker for microVM Develop.

The pinned [E2B runtime Azure Embed recipe](https://github.com/e2b-dev/runtime/blob/cf536c284434fdd2f09bbab35ec807a5dacc87e4/embed/terraform/azure/README.md) creates one Ubuntu 24.04 VM Scale Set instance intended to run Firecracker guests. That host is an Azure VM; **each Luci task subagent must instead own a separate newly created E2B/Firecracker microVM on it**. One Azure VM running four task containers would fail LC-06/15. The upstream default `Standard_D4ds_v7` is four vCPUs/16 GiB and reserves 4 GiB hugepages; it is a reference starting point, not proof that four concurrent Luci guests fit. Microsoft's [Dv5 size documentation](https://github.com/MicrosoftDocs/azure-compute-docs/blob/38164b4abefebfaac6966d71eec8c36c781b7bf9/articles/virtual-machines/sizes/general-purpose/dv5-series.md) identifies nested virtualization for a candidate family. Region, offer, zone, exact SKU, available quota, actual guest `/dev/kvm`, template capacity and cost all require later authorized verification. A capacity-aware host plan must cover the representative **12 dependency-aware tasks across four projects, four distinct concurrently owned microVMs**; four is a test configuration, not a product ceiling.

## Proposed supported boundary

| Boundary | Required design and observable refusal |
| --- | --- |
| Host and management | Put the Luci controller and E2B host behind a private Azure network. Require an authenticated TLS management gateway with pinned server identity, exact operator and task scopes, no redirects, bounded requests and audit receipts. E2B's internal port 5008 is unauthenticated and must never be directly reachable from user/public networks. The upstream Terraform opens client ports 3000–3002, uses public IPs, and is **not** a production Luci deployment as written. Refuse Azure selection until protected management and guest origins are verified. |
| Identity and secrets | Separate Luci actor/team authority, Azure host identity, E2B admin/team keys, guest attach key and the selected upstream model credential. Deliver only the task-scoped model credential to a verified guest with restricted egress. Do not copy host CLI auth stores. Upstream notes that admin/hash/team secrets live in Terraform state and VM custom data, and that its dashboard cookie is not Secure over HTTP. The production design needs a protected secret-delivery mechanism, access rotation, private state and a nonpublic browser path; Azure managed identity/Key Vault is a candidate, not an implemented claim. |
| Context, harness and result | Build an immutable, bounded task input from the accepted context revision, source digest, dependency proofs, task/attempt identity and current grants. Transfer verified bytes to a fresh microVM; keep approved context read-only to the coding user. Run an existing upstream harness through the current sandboxd/attach contract. Capture exact exit, changed files, checks and output into the independently durable store before reviewed integration or VM retirement. A model's success claim alone cannot authorize merge, checks or Deploy. |
| Persistence and host loss | Keep controller journal and accepted artifacts off the replaceable E2B VMSS OS disk. Upstream explicitly says VMSS replacement starts with fresh storage and loses templates. An independently managed controller with an Azure managed data disk, backup/snapshot and verified restore is a **candidate**, subject to atomicity, generation fencing, access and recovery design. Pin and rebuild signed templates on replacement; do not assume an Azure Blob config object is task checkpoint storage. Restore exact reservations and owned provider IDs, read back provider state **before** new dispatch, and retain unknown Create/Start/Delete without replay. |
| Ownership, capacity and cost | Give every task one durable Luci attempt ID, exact E2B VM ID, host generation and allocation/estimated-spend record. Enforce current actor/team authorization and configured concurrent CPU/memory/spend policy at effect time; backpressure under actual host and provider limits. On finish/cancel/failure, capture outputs, request exact owned VM stop/delete, prove absence and only then release Luci's active reservation. Keep unknown identity/transport/absence and retained charges visible in the primary conversation. Luci reservation, observed provider usage and final Azure invoice are three distinct facts; the pinned Embed API supplies no final invoice receipt. Deallocated Azure host compute may stop billing while disks/network persist. Never report final cost settlement from VM absence alone. |
| Deploy and teams | Develop environment is separate from the app deployment target. Reviewed candidate, independent checks, release authority, health and rollback must continue through the existing product routes. Accepted teammate amendments update exact shared context; stale attempts are stopped or reconciled without disturbing unaffected projects. A contradictory human intent stays unresolved until an authorized decision. |

## Review decisions before Azure code

1. Choose one supported subscription/region/zone and nested-virtualization SKU **after local readiness**, with actual offer and [regional/family vCPU quota](https://github.com/MicrosoftDocs/azure-compute-docs/blob/38164b4abefebfaac6966d71eec8c36c781b7bf9/articles/virtual-machines/quotas.md) checks under existing grants. Measure required host resources for four distinct guest VMs; do not treat the upstream 4-vCPU default as sufficient.
2. Specify the private network and authenticated TLS gateway for E2B management and guest origins, its access/rotation policy, model egress and attack boundary. Decide how Azure identity and secret files reach the host without upstream Terraform-state/custom-data exposure. The account permissions for VMSS, network, role assignments and any secret store must be explicit; authentication does not imply provisioning authority.
3. Specify the separately durable controller and artifact store, generation fencing, backup/snapshot schedule, tested restore, signed template rebuild and retained-running-attempt policy. [Azure managed disks](https://github.com/MicrosoftDocs/azure-compute-docs/blob/38164b4abefebfaac6966d71eec8c36c781b7bf9/articles/virtual-machines/managed-disks-overview.md) are one storage building block, not a recovery proof.
4. Pin the exact E2B runtime, guest image/template, sandboxd and upstream CLI versions, licensed material and source/build hashes. Prove the guest can consume Luci's exact context, produce bounded verifiable output and retire without public traffic or cross-task mounts. Preserve the existing AWS adapter as a separately named capability.
5. Agree the approved cost envelope, quota, resource sizes and cleanup observer for a first one-task trial, then 12/4/4 acceptance. [Azure compute billing states](https://github.com/MicrosoftDocs/azure-compute-docs/blob/38164b4abefebfaac6966d71eec8c36c781b7bf9/articles/virtual-machines/states-billing.md) distinguish stopped allocated from deallocated hosts; persistent storage/network and model use need separate accounting. No price or invoice is inferred here.

Implementation after audit should make Azure an explicit selectable provider with a fail-closed configuration and a distinct deployment identity. Then validate protected management, template and KVM before any task, run one real upstream-harness task, and expand to the 12/4/4 workload with mid-swarm amendment, conflicting outputs, independent review/check/Deploy, lost Create, cancellation, restart and host loss. Record per-task VM creation, distinct concurrent identities, exact output binding, stop/absence, retained charges and later billing evidence if an authenticated feed exists. Fixture/source checks do not pass these gates. AWS remains the later provider.
