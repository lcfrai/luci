# LOCAL-018: require settlement of the known controller

The Windows tester independently reported a controlled counterexample at `fdde0470025e612c631fb97128c6f0a8df8e99b1`: `/proc` environment scanning could omit a still-live known controller. After sending TERM, the helper relied on that scan alone and could return successful cleanup without waiting. The reported full source SHA is `d9f2276ac2aaf29a1434155d7a31c80576e5514d2e65f2fb97af084e3fd538f7`. The original local VM receipt remains with the tester; this capsule contains an independent same-function reproduction, not an invented copy of the local file.

Both added regressions fail against the original function: a live known controller omitted from the scan, and an identity observation that becomes unreadable after TERM. The same test bytes pass after correction. The exact original function bytes match the reported revision even though the surrounding adapter has the separately tested CLOUD-037 readiness wait.

Every grace, force and final settlement check now combines the owned-process scan with a fresh observation of the original controller PID/start identity. Positive absence, zombie exit or a different start identity prevents signaling a reused PID. Unreadable identity propagates as failure. A still-live controller is waited for and cannot certify success; any forced cleanup remains a failed acceptance outcome even if it later settles. Existing identity-race and permission-error tests remain.

The final explicitly enumerated helper suite passes **401 tests**, zero failed/skipped, including the two new regressions and CLOUD-037 readiness controls. Counts overlap earlier CLOUD-036 batches and are not additional unique product tests. Commands, actual exit codes, original failures and selected source bindings are retained. Tests inject observations/signals and launch no real controller, browser, Docker or model. No installed or Windows correction pass is inferred.
