**161 — the Work MCP server on the Hub behind Entra OAuth, with read-only mode; the MCP connector
allow-list.** Stream WH, 3 h, after 159 (apps: the approved-app record and its grant) and 160 (keys
and per-token limits). Two halves. **(a) The server**, new `control-plane/cmd/workmcp/`
(`main.go`, `config.go`, `mcp.go`, `tools.go`, `auth.go`, + tests), a separate binary deployed
beside the Hub (File map row `cmd/workmcp/`). It speaks MCP's **streamable HTTP** transport as
JSON-RPC 2.0 on one endpoint, protocol revision `2025-06-18` (which revisions the named clients
accept is **UNVERIFIED**; the part lists what it checked). It is hand-written on the standard
library: the module stays `go 1.23` and adds no dependency (global constraints; an SDK may replace
it later only after a licence and `go`-directive check). Methods: `initialize`,
`notifications/initialized`, `ping`, `tools/list`, `tools/call`. **Auth**, `auth.go`: every request
needs `Authorization: Bearer`; a missing or failing token gets 401 with `WWW-Authenticate: Bearer
resource_metadata="<base>/.well-known/oauth-protected-resource"`, and that document (RFC 9728) is
`{resource, authorization_servers:["https://login.microsoftonline.com/<tid>/v2.0"],
scopes_supported:["api://<hub-client-id>/Hub.Access"], bearer_methods_supported:["header"]}`. The
token is validated with the Hub's own `entra.Validator` (hub-contract §6.3, `:417-496`), so `aud` is
the Hub, `scp` holds `Hub.Access`, and `azp` must be an app an admin approved (task 159; the
desktop's id is not accepted here). `workmcp` holds **no credential of its own**: it forwards the
caller's bearer to the Hub through `hubclient` (the boundary rule: it imports `hubapi` and
`hubclient` only, never `server` or `store`), so every read and write is authorised by the Hub as
that person, and task 160's per-token limits and headers apply unchanged. **Tools** (`tools.go`),
each with a JSON Schema input: read tools `work_search {query, projectId?, limit≤50}`, `work_issue
{issue}` (an `is-…` id or a display alias; the alias is a lookup and the result always carries the
key, skeleton rule 1), `work_list {projectId, viewId?, state?}`, `work_features {projectId}`,
`work_request {request}`; write tools `work_create_issue {projectId, title, description}` (lands in
`triage`, source `app`), `work_comment {issue, body}`, `work_set {issue, priority?, labels?,
assignee?}` and `work_move {issue, to}`, whose `to` enum lists **only the human bands** (§3.3). No
tool moves to a fact state or `done`, and the Hub refuses one from an app token anyway (task 145's
guard, SW.3): two layers. Results carry text with its author class (`text·H`/`text·A`) as data.
**Read-only mode**: the endpoint `/mcp/read` never lists or dispatches a write tool, whatever the
token; and an app whose approval grants `read` (task 159) is refused writes by the Hub. **(b) The
connector allow-list** (L-197, L-256): the admin allows a connector; each person connects their
own account, and the Hub never stores a connector credential. Hub files: `store/work_mcp.go`,
`server/work_mcp.go`, matrix rows ⚑. Wire, as task 143 names it (143 wins on names):
`MCPConnector{url, name, allowedBy: User, allowedAt}`, keyed by the normalised https URL (no new id
prefix); `GET /v1/work/mcp-connectors` (any member of the org), `PUT /v1/work/mcp-connectors
{url, name}` and `DELETE /v1/work/mcp-connectors?url=` (**org admin only**); events
`work.mcp_connector_allowed` and `work.mcp_connector_removed` with `{url}`. A pure function
`ConnectorFragment(list []MCPConnector) []byte` renders the managed-settings fragment that task
166 applies as a policy layer (the key it writes, `allowedMcpServers`, is **UNVERIFIED** at the
image's pinned CLI). **Tests first:** a token for another audience is 401 with the metadata header
(mutant: the header is dropped, so clients cannot discover sign-in); an unapproved `azp` is 401
`client` (mutant: any Entra app accepted); `/mcp/read` omits every write tool from `tools/list`
and refuses `tools/call work_comment` (mutant: read-only filters the list but not the call); a
`work_move` to `done` fails schema validation in `workmcp` **and**, sent raw to the Hub with an app
token, is 403 (mutant: one layer removed); `work_issue EP-142` returns `issue:is-…@r` and no field
holds the alias as a key (mutant: alias stored); `workmcp` sends the caller's token, never a
configured one (a test config with a planted token must not reach the fake Hub; mutant: a service
token); a member's `PUT` of a connector is 403 (mutant: allow-list writable by anyone); a
connector URL that is not https is 422. Acceptance: `go test ./control-plane/cmd/workmcp/... -race
-count=1` and the Hub integration rows. Design: §1 M (L-196, L-197), P (L-244), R (L-256); §3.6.
Closes **L-196**; **L-197** and **L-256** jointly with 166 (enforcement in the sandbox) and 173
(the admin surface); the MCP half of **L-244** with 159. Does NOT claim that any named MCP client
(Claude Desktop, VS Code, Cursor) can complete Entra sign-in, because Entra has no dynamic client
registration and each client must be registered and approved (**UNVERIFIED**); nor that agents in
our sandboxes use it: they use the `panacea` verbs (05 L-196, TM-05 §0).

**162 — loops `lp-`, part 1: the record and its versions; event and schedule triggers in the
janitor, as turns of the owner's Orchestrator within their grid, billed to them.** Stream WH, 3 h,
after 145 (the W5 tables and guards) and Phase T's TM-26 (the turn queue, origin and fixed
template) and TM-37 (budgets). A loop is **a scheduled or event-driven turn of the owner's own
Orchestrator** (05 L-160, `05-design.md:322`; §3.2's row `:715`: *"trigger (event or schedule), the
owner, its autonomy bound, versions, run log"*), never a free agent. Files: new
`control-plane/internal/hub/store/work_loops.go` and `server/work_loops.go` (+ tests); ⚑
`server/janitor.go` (one loop step, after task 121's recurring-issue and reminder steps, in task
order); ⚑ `server/matrix_integration_test.go`; and one delta on Phase T's Fleet: a row in the turn
queue's deliverable-event table (`control-plane/internal/fleet/turns`, TM-26, **UNVERIFIED until
merge**) mapping `work.loop_fired` to the owner's Orchestrator queue, reached through Fleet's
per-org feed subscription (TM-01 (d)). **Wire**, in task 143's `WorkIntake` (143 wins on names):
`Loop{id:"lp-…", teamId, projectId, owner: User, name ≤80, state:"on"|"paused", pausedCause?,
currentVersion}`; `LoopVersion{loopId, version, trigger: LoopTrigger, instruction: Text (text·H of
the owner, ≤2000), action:"turn"|"start", labelId?, bound: LoopBound, savedAt, savedBy}`;
`LoopTrigger{kind:"event"|"schedule", eventKinds []string (SW.5 and SW.21 feed kinds only),
filter{labelId?, fromState?, toState?}, schedule?{every:"day"|"weekday"|"week", at:"HH:MM",
tz}}`; `LoopBound{turnsPerDay ≤ 24, levels map[actionClass]level}` using AX §7's grid names
(`ASK FIRST · PROPOSE AND WAIT · ACT AND TELL ME · FULL`, `docs/AGENTIC-UX.md:179`). Routes:
`POST /v1/projects/{projectId}/work/loops` (member; the caller becomes owner), `GET
/v1/projects/{projectId}/work/loops`, `GET /v1/work/loops/{loopId}`, `POST
/v1/work/loops/{loopId}/versions` (**owner only**, creates version n+1; versions are append-only by
grants and a trigger, as the Hub's other logs), `PATCH /v1/work/loops/{loopId} {state}` (owner; a
team admin may pause, never edit or resume). **Within their grid:** a version whose bound is wider
than the owner's own grid is 422 `loop_bound_exceeds_owner`; where Phase T stores the owner's grid

**The janitor step:** reads the feed after its own cursor, matches each `on` loop's current
version, and writes one `work.loop_fired {loopId, version, trigger, eventSeq?|scheduledFor?}` per
match, `actor: null` with `data.author` the owner (§3.6: *"janitor acts … carry `actor: null` and

fires twice; a missed schedule fires **once**, not once per missed window. The turn input stays
TM-26's fixed template: **no loop text enters it**. **Billed to them:** the turn runs on the
owner's Orchestrator and gateway token (OD-19), counts against the owner's TM-37 budget (only a
human's own message bypasses it), and its usage carries the loop id through task 135's tag
(**UNVERIFIED**, phase 6). A loop is paused with cause `owner_left` when its owner leaves the team.

janitor restart replays no firing (mutant: no unique key); three missed daily windows fire once
(mutant: catch-up burst); a paused loop never fires; a non-owner's `POST …/versions` is 403 and a

an `UPDATE` on the versions table is refused by the database (mutant: the guard only in Go);
`action:"move"` is 422 (mutant: a loop writes state, SW.3); the event's `actor` is null and
