Base: `563ac8afed4fea4f62f4b37f9178edf3dac3a3cb`. This source slice owns `desktop/src/api/azureSetup.ts`, `desktop/src/components/setup/{AzureSetup,CloudManager}.tsx`, the affected Azure setup style and tests. It does not change installer, management API, provider resources or runtime policy. Local Sol owns the installer/operator/template/image/retirement and management API identity; root owns integration and acceptance.

After generating an authenticated setup plan, the desktop can read the installer's small local `status` JSON and `azure-connection.json`. It bounds files before parsing, matches the source revision and exact private host contract, verifies the Ed25519 key's SHA-256 fingerprint, and shows uncertain stages separately from a connected workspace. It imports no credentials and stores neither file nor path. The connection section prepopulates only the private host, SSH port and user, resets any previous private-key path, and uses the existing protected SSH inspect/connect and workspace sign-in path. An observed host key differing from the pinned fingerprint blocks connection. The user must compare the pin with authenticated Azure controller readback; a local file is not independent Azure proof. A private route and SSH credential remain necessary.

Focused source checks: `cd desktop && vitest run src/components/setup/AzureSetup.test.tsx src/components/setup/CloudManager.test.tsx --maxWorkers=1 --no-file-parallelism` and `tsc --noEmit`. The tests use inert HTTP/file fixtures and do not contact Azure, Docker, an SSH server or a real workspace.

External setup and acceptance still required: the installed bundle must produce exact stage/host receipts; Azure account and route identity, VM host key, SSH access, workspace account sign-in, upstream harness execution, separate task microVMs, generation fencing, retirement, provider usage/final invoice and the 12-task/four-project/four-concurrent-VM workload need live verification. A receipt import or offline test does not mark Azure ready.
