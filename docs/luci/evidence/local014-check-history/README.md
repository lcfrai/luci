# LOCAL-014: settled unknown check history must not block new checks

On 8 October 2026, the local tester identified that `storeCheckRun` pinned every run with status `unknown`, even when exact execution cleanup had completed and no allocation remained. Successful commands that change their source intentionally leave the run unknown. Twenty such rows filled the bounded history permanently: the next check could not save its initial reservation, while recovery already reported complete for every old row.

The API regression performs twenty sequential consented HTTP checks using the existing controlled backend adapter and the real product/private-ledger lifecycle. The fixture changes source after its approval snapshot. Each command returns a successful exit and retained output, exact cleanup is confirmed, the final run remains unknown because its source changed, the completion ACK clears the ledger, and recovery reports complete. On the original implementation, check 21 returns HTTP 500 `check_reservation_failed`. The test does not seed lease rows or clear retained execution itself.

The prepared correction preserves the twenty-run history bound and the original evidence status. Unknown rows become eligible for ordinary oldest-row pruning only when a current revision explicitly records `resourcesHeld=false` and each attempted command has an allocation identity, terminal outcome and confirmed cleanup. Skipped commands require no cleanup. Queued/running runs, held resources, unknown rows missing ownership markers, missing command identities, incomplete cleanup, and partial command progress remain pinned. No user action or execution replay is introduced.
