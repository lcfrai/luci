# 03 — Work management plus agents: the landscape

**Status:** research, complete. Written 2026-09-25 for the Linear-parity workstream.

**The answer in five lines**

1. **Cross-owner Orchestrators negotiating is the one clean white space.** None of ten products
   does it; every vendor tells humans to partition the work (§12.3).
2. **Agents running inside the product is now table stakes.** Linear, GitHub and Atlassian all do
   it. Ours is narrower: long-lived steerable sessions, and Azure Repos, which Linear and
   Microsoft's own Boards integration both lack (§12.1).
3. **The provenance thread is half-copied already.** Linear ships issue → PR → release; nobody has
   brief → design → agent reason → release (§12.2).
4. **ZDR inference is hygiene, not a moat.** Atlassian and Notion Enterprise already offer it
   (§12.4).
5. **Watch Linear.** It is the only one that owns both the plan and the execution, and it shipped
   five agent products in six months (§1, §12.5).
**Question:** how do Linear, GitHub, Atlassian, Asana, Notion, ClickUp, Shortcut, Plane and new
entrants make agents first-class in work tracking, and what can none of them do that PanaceaApp can?

**Binding context:** OD-14 to OD-17 (team agents run centrally; one Orchestrator per user;
Orchestrators are the only cross-user channel; agent awareness first, calm human summary), OD-19
(org-level zero-data-retention inference through a gateway), OD-20 (cloud-first), in
`docs/superpowers/planning/2026-09-23-owner-decisions.md:114-141`.

**Builds on:** `docs/superpowers/planning/2026-09-24-team-collaboration/02-product-prior-art.md`
(§4 GitHub, §13 Linear, read 2026-09-24). This file does not repeat those findings; it extends them
to the work-tracker vendors and adds what changed or was missed.

**Clean room.** Linear, Atlassian, Asana, Notion, ClickUp, Shortcut and GitHub are proprietary:
only public sites, docs, changelogs, blogs and API docs were read, and no asset, copy or code was
taken. Plane is AGPL: only its public docs site was read, never its source. Every source URL is
listed in §14 with the date read. "UNVERIFIED" marks any claim taken from a search-result summary
rather than a page actually fetched, or not confirmed at all.

## 1. Linear — the benchmark

Linear has moved fastest. In six months of 2026 it shipped a first-party agent, code access,
releases, coding sessions and recurring agent jobs, all on one issue model.

| Date | Shipped | Source |
|---|---|---|
| 24 Mar 2026 | **Linear Agent**: `Cmd/Ctrl+J` chat, `@Linear` in any comment, Slack and Teams; saved **skills** | [L4] |
| 30 Apr 2026 | **Releases**: CI/CD pipelines; a CI step "scans the new commits for Linear issue references (e.g. ENG-123)" and attaches them to a release; continuous or scheduled pipelines; release notes generated by Linear Agent | [L9] |
| 14 May 2026 | **Code Intelligence**: "controlled access to your codebase", GitHub integration only | [L5] |
| 11 Jun 2026 | **Coding sessions**: "Linear Agent can now write code using Claude Code and Codex" | [L2], [L6] |
| 20 Jul 2026 | **Loops**: recurring agent work "on a schedule or in response to an event" | [L7] |
| 20 Aug 2026 | Coding sessions gain environments, browser use and runtime pricing (page 404ed; title only) | [L2] |
| 14 Sep 2026 | Loops can edit documents and post to Slack | [L2] |

**How an agent gets work.** Three ways: **delegate** the issue, **@mention** the agent in a
comment or description, or chat. "The human assignee remains responsible for the issue, even after
delegation to an agent" [L1]. Third-party agents install as an OAuth **app actor** with the scopes
`app:assignable` ("be assigned as a delegate on issues") and `app:mentionable` [L3]. Loops add a
fourth route: a schedule or an event, such as an issue entering triage [L4], [L7].

**How progress is shown.** Each engagement is an **AgentSession** with six states: `pending`,
`active`, `error`, `awaitingInput`, `complete`, `stale`. Linear sets the state from the agent's
emitted activities; "no manual state management is required" [L3]. Agents emit five activity
types (`thought`, `elicitation`, `action`, `response`, `error`); the human's reply is a `prompt`.
An agent must "emit a `thought` activity within 10 seconds" of being delegated. **Plans** are a
session checklist with steps `pending | inProgress | completed | canceled`. `thought` and `action`
can be **ephemeral**, replaced by the next one, so the issue shows one live line rather than a log
[L8]. Coding sessions draft a PR and "add a diff to the issue" [L6]. Agent user pages, a Delegate
filter and Insights sliced by delegate give the portfolio view [L1].

**How humans stay in control.** Delegate is not owner: the human stays the assignee [L1]. Admins
install agents, choose "which teams the agent has access to", and agents cannot "sign in to the
app, access admin functionality or manage users" [L1]. Workspace and team **Additional guidance**
steers agents; "team guidance takes priority" [L1]. Loop instructions and every run are
inspectable by "anyone with access" [L7]. The public docs read say nothing on how a human stops a
running session [L8] (UNVERIFIED either way).

**How multiple agents coordinate.** They do not, beyond the board. Nothing read describes
agent-to-agent hand-off, two agents on one issue, or conflict detection [L3], [L8]. Linear Agent
itself runs the coding session; third-party agents (Cursor, Devin, Codex, Factory) each attach to
issues separately. Coordination is humans partitioning work into issues.

**How work links to code, review and release.** The strongest chain on the market: issue →
Code Intelligence context → coding session → draft PR with diff on the issue → Releases moves the
issue when its release completes → agent-written release notes [L5], [L6], [L9]. The link is an
**issue key in a commit message**, not a record of which brief, design or agent produced the change.
Code Intelligence and coding sessions are **GitHub only** in every page read; the release tool is
an open-source CLI that "supports other CI/CD systems" [L9], so Azure Pipelines could feed it, but
no Azure DevOps repository integration was found.

**Enterprise posture.** SOC 2 Type II, ISO 27001:2022, HIPAA BAA, EU or US data residency chosen
at workspace creation, SAML, SCIM, IP restrictions, three months of audit log [L10]. SaaS only.
AI runs on pooled **AI credits** (Loops launched with "$20 per seat" of promotional credit) [L7].
Coding sessions default to "GPT-6 Sol"; admins can pick Claude Opus 5.5 or Sonnet 5 [L6]. No
public page read states model-provider retention terms for coding sessions: **UNVERIFIED**.
Enterprise-managed MCP authorisation with Okta arrived 13 Aug 2026 [L2].

**Where Linear stops.** Its agent is a guest in a sandbox Linear rents, on a board. It has no
brief-to-design phase, no design canvas, no per-user orchestrator, no live file-level awareness
between agents, GitHub only, and pooled credits rather than per-user attributed inference.

## 2. GitHub — Projects, the Copilot cloud agent and Agent HQ

The earlier file covers mission control and Copilot Memory (02-product-prior-art §4). New here:

**How an agent gets work.** Assign the issue to Copilot, Claude, Codex "or all three" from the
Assignees dropdown; each opens a draft PR [G3]. Also `@copilot` on a PR, the agents panel, VS
Code, and "Microsoft Teams, Slack, **Azure Boards**, JIRA, and Linear" integrations [G1]. Copilot
can run "on a schedule or in response to events" [G1]. Dependabot alerts became assignable to
agents on 7 Apr 2026 [G5] (search summary, UNVERIFIED). GitHub is the only vendor found that takes
work **from Azure Boards**; the code must still live on GitHub [G1].

**How progress is shown.** Since 26 Mar 2026 an agent session sits "directly under the assignee in
the sidebar" with four states, **"queued", "working", "waiting for review", "completed"**, and
Projects table and board views get a **"Show agent sessions"** toggle [G2]. Session logs show
research and plan before the PR; "every step happening in a commit" [G1].

**How humans stay in control.** The agent opens a PR; a human merges it. Enterprise admins enable
agents by policy and repositories can opt out [G1]. The **agent control plane** (GA 26 Feb 2026)
lets admins choose which agents and models are available "per team and per repository", set task
policies, and audit agent sessions with an `actor_is_agent` flag and `agent_session.task` start,
finish and failure events [G4] (search summaries, UNVERIFIED in detail). Custom agents are defined
centrally in `.github-private/agents/*.md` [G4] (UNVERIFIED).

**How multiple agents coordinate.** They race. Assigning "all three" yields three competing draft
PRs for a human to pick from [G3]. GitHub's own advice is "be thoughtful about partitioning work"
(02 §4). Copilot Memory shares cited, validated repository facts across agents asynchronously
(02 §4). No live awareness or negotiation.

**How work links to code, review and release.** Native and deep: issue → branch → draft PR →
review → merge → Actions → Releases, all in one product. PR lifecycle metrics for agent PRs come
through the usage metrics APIs [G1]. There is no brief or design artefact upstream of the issue.

**Enterprise posture.** GitHub Enterprise Cloud with SSO, audit log and a data-residency option
(from prior knowledge, not re-read today: UNVERIFIED); the agent
runs in GitHub Actions runners, one repository, one branch, one PR, **59 minutes** maximum [G1].
Billed as Actions minutes plus premium requests under the org's Copilot plan (02 §4). The only
host is GitHub, which rules it out as the whole answer under OD-4 (Azure DevOps and GitHub).

**Where GitHub stops.** Best code-to-release chain and best admin plane, but the agent is a
59-minute contractor per issue. No per-user orchestrator, no cross-owner channel, nothing before
the issue exists, and the three-agent race is parallel waste, not coordination.

## 3. Atlassian — Jira, Rovo agents and Rovo Dev

**How an agent gets work.** "Agents in Jira" (announced 25 Feb 2026 [A1]; GA for Standard,
Premium and Enterprise in May 2026, search summary, UNVERIFIED) gives four routes: the **Agent
picker**, "@mention an agent in a comment", a **workflow transition** so the agent triggers "when
any team member moves a work item to the allocated status", and, in team-managed spaces, "add an
agent to a column on the board" [A2]. Unlike Linear, **the agent is the assignee**, "with the same
fields and patterns your teams already know" [A1]. Jira Automation has an "Invoke Rovo Agent"
action, and since August 2026 "Claude, GitHub Copilot, and Cursor are now native action steps
inside Jira Automation rules" [A3] (third-party blog). "GitHub Copilot coding agent, the first of
many partner agents" is assignable from Jira [A2]. **Rovo Dev** starts a coding session from a
"Generate code with Rovo Dev" panel on the work item (search summary of [A4], UNVERIFIED).

**How progress is shown.** An **Agents** section on the work item [A2]; the board shows which
items are delegated to agents and their status [A1]. Rovo Dev notifies in-app and in Slack when
work is ready and pushes a draft PR to Bitbucket [A4] (UNVERIFIED).

**How humans stay in control.** A sharp and unusual rule: "only the person who adds the agent as
an assignee … can interact with the agent directly. However, anyone with access to the work item
can see that an agent has been triggered" [A2]. That is close to OD-16 (nobody steers another
user's agent), but enforced per work item, not per user. Agents respect existing "permissions,
project configurations, workflows, and audit trails" [A1]. Admins govern who can create agents
and mark agents as verified [A5]. Each invocation spends **Rovo credits**, with overage policies
set in Atlassian Administration [A2].

**How multiple agents coordinate.** Jira is pitched as "the center of gravity" for mixed teams,
against "agent sprawl" where "most agent work today happens in one-off chats that never make it
back to where the work lives" [A1]. The mechanism is still the workflow: one agent per transition,
hand-off by status change. The Teamwork Graph gives every agent the same org context [A6]. No
agent-to-agent negotiation was found. Whether two agents can sit on one work item is not stated
[A2].

**How work links to code, review and release.** Bitbucket natively, GitHub via the Copilot agent,
and "Code Context" that lets Rovo and coding agents "reason across multi-repo codebases" through
the Teamwork Graph (Aug 2026) [A3]. Confluence holds the spec, so a brief-to-code chain exists
across two products, joined by links rather than one artefact.

**Enterprise posture: the strongest AI data terms of the trackers.** "The LLM providers we use do
not retain your inputs and outputs, or use them to improve their services"; models include
Anthropic Claude, OpenAI GPT and Google Gemini plus open models; Enterprise can "elect to use only
Atlassian-hosted LLMs" inside the Atlassian Cloud boundary; data residency covers Rovo [A7].
Atlassian's residency list includes Australia (prior knowledge, UNVERIFIED today).

**Where Atlassian stops.** The agent is a workflow step. Zero-retention inference, residency and
agents-as-assignees are already shipped here, so **ZDR alone is not white space**. What is
missing: agents running a whole lane inside the product, a per-user orchestrator, live awareness
between agents, and one artefact from brief to release.

## 4. Asana — AI Teammates and "Agentic Work Management"

**How an agent gets work.** Assign a task to an AI Teammate "as you would team members",
@mention it, or trigger it from rules [S1]. 4 Jun 2026 relaunch as "Agentic Work Management", an
"operating system for human-agent teams" with **Dash**, an agent that "understands goals,
priorities and what work needs attention across teams and tools" and routes alerts to people [S2].
More than 30 prebuilt teammates [S1] (search summaries say 12 or 21 at earlier dates).

**How progress is shown.** "A real-time indicator of its work" plus "AI action logs – a full trail
of every action such as tasks created, comments posted, searches performed, objects modified".
Results are "visible to anyone with access, not solely the person who triggered the agent" [S3].

**How humans stay in control.** Checkpoints: "Before performing any privacy-sensitive action,
Teammates must get explicit user approval, a hard constraint built into the system." Users can
ask "why" and get an explanation "from the same context they used to make the decision". Memory is
"fully inspectable … every memory their Teammate holds, right on its profile" [S3]. Teammates are
**team-scoped, not personal**: "Only a specific set of people (often an Asana team) is permitted to
trigger action from a teammate" [S3]. Permissions follow Asana's own model [S1].

**How multiple agents coordinate.** "Multiple AI Teammates can work on the same initiatives
simultaneously" [S1], but no page read describes one Teammate talking to another [S3]. Dash is the
closest thing to an orchestrator, and it routes to humans, not to agents [S2].

**How work links to code, review and release.** Weak. A developer-facing "Command" app was
announced [S2]; integrations are Gmail, Outlook, Slack, HubSpot, Figma, Canva and similar [S2]. No
coding agent, PR or release link was found.

**Enterprise posture.** Customer data "not used to train AI models"; Enterprise customers "can
select preferred AI partners"; configurable data residency [S1]. No zero-retention statement found
on the pages read (UNVERIFIED either way).

**Where Asana stops.** Best human-control vocabulary of the set (checkpoint, ask-why, inspectable
memory, team-scoped agent), no software delivery at all.

## 5. Notion — Custom Agents and External Agents

**Network note.** Every `notion.com` page (releases, help) returned a 302 to the KPMG intranet on
2026-09-25. **Everything in this section is from search-result summaries and is UNVERIFIED.**

**How an agent gets work.** **Custom Agents** (Notion 3.3, 24 Feb 2026 [N1]) are given "a job,
set a trigger or schedule" and run "completely autonomous (no manual prompting)" [N2]; since 31
Jul 2026 a finished AI Meeting Note can trigger one [N3]. **External Agents** (Notion 3.6, 1 Jul
2026) bring in agents "from Claude, Cursor, Codex, and Decagon", which a team can "assign them
tasks on a shared board, mention them the way you'd mention a teammate, and watch execution happen
inside the same workspace" [N4]. Notion 3.7 (15 Sep 2026) adds "Agent skills for your whole team"
[N5].

**How progress is shown.** Execution is watched on the board [N4]; run logs, version history and
usage analytics exist for Custom Agents (third-party summary [N6]).

**How humans stay in control.** "Each Custom Agent gets its own permissions, just like a
teammate"; they "operate only on the pages, databases, and external tools you explicitly grant"
[N2]. Kill switches and AI activity logs by user and event (third-party summaries [N6], [N7]).

**How multiple agents coordinate.** Through a shared board, which one third-party post calls
using Notion "to coordinate agents" [N4]. No agent-to-agent protocol found.

**How work links to code, review and release.** Only through the External Agents' own products
(Cursor, Claude, Codex). Notion is the brief and the board, not the repository.

**Enterprise posture.** Enterprise: LLM providers (Anthropic for queries, OpenAI for embeddings)
under zero data retention; other plans up to 30 days [N7]. SOC 2 Type II and ISO 27001 [N8].
Custom Agents use Notion credits on Business and Enterprise from 4 May 2026 [N2].

**Where Notion stops.** It is the closest to our **Define** phase (docs plus agents plus board), and
it now hosts outside coding agents, but it owns no sandbox, no code and no release.

## 6. ClickUp — Super Agents, plus Codegen

**How an agent gets work.** Super Agents can be triggered "automatically or manually" [C1]; a
search summary says you can set one "as a task assignee", @mention it, or message it directly
(UNVERIFIED). ClickUp **acquired Codegen** (a coding-agent start-up) on 23 Dec 2025 and retired
the standalone product on 16 Jan 2026 [C2] (search summaries). Codegen "reads the surrounding task
context, writes the code, opens a pull request, and reports its progress inside ClickUp" [C3]
(search summary, UNVERIFIED); ClickUp's own post promises details "in the months ahead" and names
no git host or sandbox [C4].

**How progress is shown.** A "Super Agent Activity" view exists, not described on the page read
[C1].

**How humans stay in control.** Super Agents "seek human approval for critical decisions"; admins
choose "which tools and data sources they can access and who in your Workspace can trigger and
manage them" [C1].

**How multiple agents coordinate.** Not described [C1].

**How work links to code, review and release.** Task → Codegen → PR is the stated path [C3]; no
release link found.

**Enterprise posture.** Not established from pages read today (UNVERIFIED).

**Where ClickUp stops.** It bought a coding agent to close the gap to code. That shows the
direction of the market: trackers are buying execution. Nine months after the deal, no shipped
coding product was found on the pages read.

## 7. Shortcut — Korey and "Shortcut for Agents"

**How an agent gets work.** "Shortcut for Agents" (6 May 2025 release note; blog 20 May 2025):
"Agents can be treated just like team members in Shortcut: assigned Stories, tagged in comments,
tracked in workflows, and visible in updates" [H1], [H2]. Devin is activated by making it the
**Story owner**; Claude and others connect through the Shortcut MCP server (24 Mar 2025) [H1],
[H2]. **Korey**, Shortcut's own agent (30 Sep 2025), "writes specs, tracks progress" and is reached
by assignment, `@korey` in Slack, a right-click menu (10 Feb 2026) and a Chrome extension (20 Apr
2026) [H2].

**How progress is shown.** Assigned agents such as Devin "automatically progress Stories through
key workflow stages, such as 'In Development' and 'Ready for Review'", keeping "all communication
and updates within Story comments" (search summary of [H3], UNVERIFIED).

**How humans stay in control.** "You stay in control" [H1]; no governance mechanism is described.

**How multiple agents coordinate.** Korey shapes the story; Devin builds it. That is a two-agent
relay by role, joined by the Story, and the only explicit spec-agent-then-code-agent hand-off
found among the trackers [H1].

**How work links to code, review and release.** Via the agent's own PR (Devin) and Shortcut's
existing GitHub integration. API v4 alpha (12 May 2026) is "to … optimize agent compatibility"
[H2].

**Enterprise posture.** Not established from pages read today (UNVERIFIED).

**Where Shortcut stops.** A small vendor that pioneered agents-as-owners in May 2025, a year before
Jira, but has shipped little since beyond Korey entry points.

## 8. Plane — public docs and blog only (source is AGPL and was not opened)

**How an agent gets work.** "Agents in Plane" launched **18 Sep 2026**: assignment to a work item,
a mention in a conversation, or a schedule or event [P1]. The product page says an agent can be
added "as an assignee, the same as any teammate" (search summary of [P2], UNVERIFIED). Templates
include a Spec Writer and a Standup Summarizer (search summary, UNVERIFIED).

**How progress is shown.** Not described in the launch post [P1].

**How humans stay in control.** Each agent is defined by "objective, scope, permissible actions,
constraints, and escalation points"; "anything outside it comes back to a human" [P1]. Plane's
enterprise guidance lays out an autonomy ladder, **Read → Recommend → Draft → Approval-gated →
Bounded autonomous**, and a permission chain "identity → Plane permission → tool exposure → action
authorization → approval → write execution" [P3]. Enterprise Grid adds approval flows, transition
conditions and workspace audit logs [P3].

**How multiple agents coordinate.** Not described. Plane's guidance does name the failure modes
multi-agent systems hit: "stale state", "repeated execution", "concurrent changes", "event loops:
depth limits and circuit breakers", and prompt injection from retrieved content [P3].

**How work links to code, review and release.** An MCP server with 28 tools covers "work items,
cycles, and releases" [P3]; the coding itself is someone else's agent.

**Enterprise posture: the self-hosting outlier.** Plane runs self-hosted and air-gapped, and
states: "Project-system location, agent-runtime location, network path, and inference location
should each be documented separately"; inference can be local, private endpoint, external API or
hybrid [P3]. Agent credits are a shared workspace pool, 100 to 200 per seat per month [P1].

**Where Plane stops.** The only tracker a regulated customer can host alone, with the clearest
written agent-governance model. But its agents are bounded tracker jobs, not builders.

## 9. Azure Boards with the Copilot cloud agent — what KPMG already has

Not on the brief's list, but it is the incumbent for a Microsoft shop, so it is the real baseline.
Source: Microsoft Learn page, dated 17 Jun 2026, updated 23 Jul 2026 [M1].

- **Gets work:** from a work item, "Create a pull request with GitHub Copilot", pick a repository
  and branch, add optional instructions [M1]. GitHub custom agents appear in Azure DevOps (Sprint
  269 notes, search summary [M2], UNVERIFIED).
- **Progress:** three states on the work item, **In Progress, Ready for Review, Error**, and a
  Copilot icon on the board card; "expect the Copilot operation to take 5-15 minutes" [M1].
- **Control:** a hard gap: "After starting a GitHub Copilot operation from a work item, **you
  can't cancel it**. The Copilot coding agent runs to completion" [M1].
- **Coordination:** none: "Copilot doesn't handle dependencies between work items. Keep each
  work item self-contained" [M1].
- **Code link:** branch, draft PR and merge commit link back to the work item [M1]. But
  "**Azure Repos (Azure DevOps Git repositories) aren't supported**" [M1]; the code must be on
  GitHub.
- **Context passed:** only "the work item title, large text fields, comments, and the work item
  link" [M1]. The brief, the design and the other agents are not in it.

For KPMG this is the sharpest competitor gap: the tracker is Microsoft's, but its agent cannot
touch Azure Repos, cannot be stopped, and knows nothing beyond one work item.

## 12. The white space: the four candidates, tested

### 12.1 Agents actually running inside the product — **no longer white space**

Linear runs Claude Code and Codex "in a managed development sandbox" since 11 Jun 2026 [L6];
GitHub runs Copilot, Claude and Codex in Actions [G1], [G3]; Rovo Dev codes from a Jira work item
[A4]. "The agent runs here" is now table stakes. What is still ours, and narrower:

- **Long-lived, steerable sessions.** GitHub stops at **59 minutes** and one PR [G1]; an Azure
  Boards run "can't cancel" [M1]. Our cockpit streams and steers an unmodified Claude Code session
  for as long as the work takes. Copy time for Linear or GitHub: **months**. It is a product
  choice, not a hard problem.
- **Azure Repos.** Linear is GitHub-only [L5], [L6]; Microsoft's own Boards integration says
  "Azure Repos … aren't supported" [M1]. OD-4 needs both. For KPMG this is a concrete, current gap.
  Copy time: Microsoft could close it whenever it chooses; it has not in the year since the
  preview (Sep 2025 [M3], search summary).
- **Kata microVM per session** on Azure (OD-14, OD-18). Nobody publishes their sandbox isolation
  model in the pages read (UNVERIFIED either way), so this is a trust claim, not a visible feature.

### 12.2 One provenance thread from brief to release — **partly real**

The **issue-to-release** half is shipped: Linear's Releases attach issues found by key in commit
messages and write notes with its agent [L9]; GitHub has issue → PR → release natively; Jira has
Confluence spec → work item → Bitbucket. What none has is the **front half and the "why"**: a brief
section that a design frame cites, that each agent task carries as its **reason** (05-design §0
item 3), and that the release carries back. Their link is a key in a commit message; ours is the
same artefact. And none has a Design phase: no tracker here has a design canvas that agents edit
(OD-11).

**Copy risk: Linear, within about two to three quarters.** It already owns Docs, Projects, Code
Intelligence, coding sessions and Releases [L4]-[L9]; rolling "project doc → issues → release"
into one view is assembly, not invention. The Design phase is what they cannot copy quickly.

### 12.3 Cross-owner Orchestrators negotiating — **the one clean differentiator**

Not one of the ten products does it. The nearest things are all weaker:

| Nearest thing | Why it is not this |
|---|---|
| GitHub: "all three" agents on one issue [G3] | a race for a human to judge, not a negotiation |
| Jira: only the assigner may talk to the agent [A2] | control, which OD-16 also has, but no agent-to-agent channel |
| Shortcut: Korey writes the Story, Devin builds it [H1] | a relay by role, one owner |
| Cline Kanban: dependent tasks auto-start [E1] | one user, local, sequence only |
| Devin coordinator (02 §2) | top-down, one user's tree |
| Azure Boards: "doesn't handle dependencies" [M1] | explicitly absent |

Every vendor's advice is the same: humans partition the work ("be thoughtful about partitioning
work", 02 §4). OD-16's design (typed `ask`/`propose`/`accept`, leases, forecast conflicts,
inform-or-decide escalation, 05-design §6) replaces human partitioning with agent negotiation.

**Why it is hard to copy.** It needs three things at once: the platform must **observe** every
agent's file activity live (trackers do not run the agents; third-party agents run in vendor
clouds the tracker cannot see); a **per-user orchestrator** with a protocol; and an **injection
fence**, because one user's agent text reaches another user's agent (05-design §7). **GitHub** is
best placed (it runs every agent in Actions and owns the merge) at perhaps **6 to 12 months**;
Linear next. It is a lead, not a moat. **Risk:** it is designed, not built, and not proven wanted;
no one having shipped it may mean users do not ask for it.

### 12.4 Managed zero-data-retention inference — **not a differentiator**

Atlassian already says "the LLM providers we use do not retain your inputs and outputs", offers
Atlassian-hosted LLMs and residency for Rovo [A7]. Notion Enterprise has provider ZDR [N7]
(UNVERIFIED). Plane lets a customer put inference anywhere, including air-gapped [P3]. ZDR is
**hygiene** for a regulated buyer. Two narrower points are ours: the **AU path selectable per
project by data classification** (OD-19), and **per-user attributed usage** where Linear, Jira,
Notion and Plane pool credits [L7], [A2], [N2], [P1]. Both are copyable in weeks by anyone with a
gateway; they help win a KPMG review, they do not win a market.

### 12.5 The verdict: the combination is the product

| Candidate | Real differentiator? | Who could copy, how fast |
|---|---|---|
| Cross-owner orchestrators negotiating | **Yes, the only clean one** | GitHub 6-12 months; Linear after |
| One thread brief → design → release | **Partly**: the front half and the "why" | Linear 2-3 quarters, minus the Design phase |
| Agents running in the product | **No** as stated; **yes** for long-lived steerable sessions on Azure Repos | anyone, months; Microsoft on Azure Repos whenever it chooses |
| Managed ZDR inference | **No**; hygiene | anyone with a gateway, weeks |

The market splits in two. **Trackers** (Jira, Asana, Notion, ClickUp, Shortcut, Plane) own the
plan and rent the execution from Copilot, Cursor, Devin or Claude. **Executors** (GitHub, Devin,
Cursor) own the execution and start at the issue. **Linear is the only one crossing over**, and it
is doing so fast: agent, code access, releases, coding sessions and loops in six months [L2].

PanaceaApp's claim is that it owns **the whole line, for a team**: the brief, the design, the
agents running for each person, the agents talking to each other across people, and the release,
on one thread. No one else has more than two of those five. That combination is the "magic" in
the owner's ask; each piece alone is copyable.

**Watch Linear most closely.** It is the only competitor that already owns both plan and
execution, and its six-month pace would reach the thread's back half next.

## 13. What to take, as ideas only (clean room: no copy, assets or code)

Do now, cheap, because they close parity gaps a Linear user will notice:

1. **Delegate is not owner** [L1]: a human stays accountable for every agent task. It already
   matches OD-16.
2. **Acknowledge within seconds, one live line** [L8]: Linear requires a `thought` within 10
   seconds and replaces ephemeral lines, so an issue shows one current line, not a log. This fits
   the design system's one-heartbeat rule.
3. **Plan as a checklist with four step states** [L8], shown on the task card.
4. **Ask-why and inspectable memory** [S3]: any human can ask an agent why, and see what it
   remembers.
5. **`actor_is_agent` on every audit row** [G4] and **Plane's autonomy ladder** (read, recommend,
   draft, approval-gated, bounded) as the per-team policy vocabulary [P3].

Later: Linear-style **Loops** (scheduled and event-triggered agent work) [L7]; an **agent icon on
the board card** [M1]; Jira's **agent on a workflow transition or board column** [A2].

**One tension to settle, not settled here.** 02-product-prior-art §13 advised integrating with
Azure Boards and GitHub Issues "rather than building a tracker". The owner now asks for everything
Linear does. Both can hold if PanaceaApp's own work view is first-class and it still syncs to
Boards, Jira and GitHub Issues, because KPMG teams will not leave Azure Boards on day one.
