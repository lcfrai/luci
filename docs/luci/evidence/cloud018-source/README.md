# CLOUD-018: automatic retained task completion

Manual task sessions now have a durable, bounded completion observer. An exited session is joined to its exact reviewed operation, its safe retained report is captured, and review/question attention is published without an explicit Check team status or report-capture request. This continues after controller restart, with an empty queue and with future dispatch paused. Worker claims remain separate from controller-recorded checks and integration.

[Verification receipt](verification.json) preserves two race-enabled source batches: the first has **356 passing test outcomes and 3 expected Windows-only skips**; the final narrow queue-read correction has **14 passing outcomes and no skips**. Counts include subtests and the second batch repeats some cases. Each batch has an unchanged 674-input Go/module manifest; these are dirty-source checks based on `29be4018f951ba2b3f33ae63067e4b7257da0c7a`. That base revision alone does not contain the correction; compare the recorded final source hashes with the eventual integrated revision. Exact names, commands, timestamps, source hashes and raw-artifact hashes are retained beside the receipt.

The observer scans at most 128 registry metadata rows and handles at most 8 candidates in a bounded turn. Busy, uncertain or unreadable ownership remains unmarked and retriable. A completion watermark cannot carry across a changed session generation. The observation path does not start work, integrate changes, approve results, impersonate the original user or release a still-retained stopped allocation. Local warnings report changed observation errors with bounded text.

A malformed private queue cannot block publication of an independently proven terminal status. Report capture still requires trustworthy ownership; it stays pending until that data is restored. The regression preserves the corrupt bytes, refuses dispatch and proves subsequent collection without manually editing the run or registry.

The tests use actual HTTP handlers, private Git/context files, persistent registry state and the real reaper, with controlled backend states. They do not establish native Docker/Windows behavior, live-model quality or installed UI completion. Matching-package continuation acceptance and the selected-view refresh are separate gates. The prior full Go run’s unrelated terminal-transport failure remains recorded; these affected checks are not a replacement full-suite claim.
