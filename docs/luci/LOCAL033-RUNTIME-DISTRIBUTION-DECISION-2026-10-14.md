# LOCAL-033 runtime installation decision for root review

**Status:** proposed architecture choice, not an implemented or accepted fix. Product source is based on main `563ac8afed4fea4f62f4b37f9178edf3dac3a3cb`; the Azure UI branch adds no runtime changes. The original warm-build Windows receipt is `recovery-79b5277b/LOCAL033-warm-build-attribution.json` in the local acceptance evidence (not retrieved in this cloud workspace).

## Evidence and choice

The reported normal warm install began with 3.792 GB available and a 1 GiB RUN limit. Go, apt and npm stages ran in sequence; the npm stage crossed the 1 GiB host reserve and the owned monitor cancelled the exact build. Cancellation positively settled and released its lease. The reported WSL guest cache growth was approximately 2.148 GB while anonymous memory grew only about 12 MiB. This supports retained daemon/guest cache outside the RUN cgroup, not a failed RUN cap. The existing `images/sandbox/Dockerfile` compiles Go and installs OS packages plus three upstream CLIs on the user's PC. `runtime_image.go` sets `NoCache: true`; `runtime_image_context.go` inserts allocation-specific labels after both `FROM` lines, which also makes all following layers allocation-specific. A cache flag change alone does not give a reusable warm path.

**Choose a source-bound prebuilt OCI runtime as the ordinary installed setup path**, produced once in the trusted release pipeline on an adequately provisioned Linux builder. Retain the current local build only as an explicitly selected advanced fallback behind its unchanged admission and owned-cancellation guards. The ordinary path must not require host Codex/Claude login or run an upstream coding harness outside Docker. This choice avoids repeated Go/apt/npm RUNs on a low-memory Windows PC, while still requiring measured installed import and host-reserve evidence before claiming LOCAL-033 fixed.

## Proposed source joins

1. `scripts/build-release.{sh,ps1}` and release/package manifests: consume a release-built OCI archive with an exact source revision, every runtime-context input hash, archive SHA-256, image config ID, image inventory and licence bindings. Verify before packaging; make it available to the installed app without a source checkout or secret-bearing URL. Confirm native/portable package-size support rather than silently omitting the asset.
2. `control-plane/internal/backend/dockerbe/runtime_image*.go` and `internal/backend/runtime_image.go`: stream the bounded archive into Docker only after regular-file, source-manifest, archive and daemon-engine checks. Refuse an archive with any repository tag that could overwrite an unrelated image. Read back the exact imported image ID and expected config. Create only a lightweight allocation-labeled derivative from the immutable imported ID; keep exact labels for ownership and cancellation. No Go/apt/npm RUN is needed locally on this path.
3. `control-plane/internal/api/{runtime_install_execution.go,execution_runtime_image_leases.go}`: use the existing authenticated setup actor/current authority and exact engine/instance/source/allocation lineage, admission ledger, pending-effect journal and no-blind-retry rules. Distinguish archive import, derivative creation and publication; retain uncertainty/charge when Docker load or stream settlement is unknown. Reconcile by exact immutable image/config/label readback, never absence alone. Keep cold-download/import demand distinct from the worker RUN limit and preserve fresh whole-machine reserve monitoring.
4. `desktop` setup status: show verified matching archive availability, missing asset, ongoing/uncertain import and exact recovery action without displaying a successful runtime until final readback and publication.

No global WSL setting, cache drop, Docker prune, unrelated image mutation or lowered reserve is part of this choice. If the OCI archive cannot be packaged reliably for the normal installer, root should reconcile a version-bound authenticated download with the same manifest and fail-closed verification before code switches distribution mode.

## Minimum evidence before closure

Preserve the two original Windows failed builds. Focused offline tests should cover manifest/source mismatch, oversized or tagged archive refusal, wrong image/config/engine, duplicate and lost import response, cancel/restart with retained lease and unrelated image preservation. The installed Windows retest must measure every stage's host/WSL memory, actual reserve, Docker image identity, no local heavy RUN, genuine upstream Docker harness execution and owned cleanup. A source test or image load alone does not close LOCAL-033 or product acceptance.
