# 03 — Work management plus agents: the landscape

**Status:** research, in progress. Written 2026-09-25 for the Linear-parity workstream.
**Question:** how do Linear, GitHub, Atlassian, Asana, Notion, ClickUp, Shortcut, Plane and new
entrants make agents first-class in work tracking, and what can none of them do that PanaceaApp can?

**Binding context:** OD-14 to OD-17 (team agents run centrally; one Orchestrator per user;
Orchestrators are the only cross-user channel; agent awareness first, calm human summary), OD-19
(org-level zero-data-retention inference through a gateway), OD-20 (cloud-first), in
`docs/superpowers/planning/2026-09-23-owner-decisions.md:114-141`.

**Builds on:** `docs/superpowers/planning/2026-09-24-team-collaboration/02-product-prior-art.md`
(§4 GitHub, §13 Linear, read 2026-09-24). This file does not repeat those findings; it extends them
to the work-tracker vendors and adds what changed or was missed.

**Clean room.** Linear, Atlassian, Asana, Notion, ClickUp, Shortcut and GitHub are proprietary:
only public sites, docs, changelogs, blogs and API docs were read, and no asset, copy or code was
taken. Plane is AGPL: only its public docs site was read, never its source. Every source URL is
listed in §12 with the date read. "UNVERIFIED" marks any claim taken from a search-result summary
rather than a page actually fetched, or not confirmed at all.

## 1. Linear — the benchmark

Linear has moved fastest. In six months of 2026 it shipped a first-party agent, code access,
releases, coding sessions and recurring agent jobs, all on one issue model.

| Date | Shipped | Source |
|---|---|---|
| 24 Mar 2026 | **Linear Agent**: `Cmd/Ctrl+J` chat, `@Linear` in any comment, Slack and Teams; saved **skills** | [L4] |
| 30 Apr 2026 | **Releases**: CI/CD pipelines; a CI step "scans the new commits for Linear issue references (e.g. ENG-123)" and attaches them to a release; continuous or scheduled pipelines; release notes generated by Linear Agent | [L9] |
| 14 May 2026 | **Code Intelligence**: "controlled access to your codebase", GitHub integration only | [L5] |
| 11 Jun 2026 | **Coding sessions**: "Linear Agent can now write code using Claude Code and Codex" | [L2], [L6] |
| 20 Jul 2026 | **Loops**: recurring agent work "on a schedule or in response to an event" | [L7] |
| 20 Aug 2026 | Coding sessions gain environments, browser use and runtime pricing (page 404ed; title only) | [L2] |
| 14 Sep 2026 | Loops can edit documents and post to Slack | [L2] |

**How an agent gets work.** Three ways: **delegate** the issue, **@mention** the agent in a
comment or description, or chat. "The human assignee remains responsible for the issue, even after
delegation to an agent" [L1]. Third-party agents install as an OAuth **app actor** with the scopes
`app:assignable` ("be assigned as a delegate on issues") and `app:mentionable` [L3]. Loops add a
fourth route: a schedule or an event, such as an issue entering triage [L4], [L7].

**How progress is shown.** Each engagement is an **AgentSession** with six states: `pending`,
`active`, `error`, `awaitingInput`, `complete`, `stale`. Linear sets the state from the agent's
emitted activities; "no manual state management is required" [L3]. Agents emit five activity
types (`thought`, `elicitation`, `action`, `response`, `error`); the human's reply is a `prompt`.
An agent must "emit a `thought` activity within 10 seconds" of being delegated. **Plans** are a
session checklist with steps `pending | inProgress | completed | canceled`. `thought` and `action`
can be **ephemeral**, replaced by the next one, so the issue shows one live line rather than a log
[L8]. Coding sessions draft a PR and "add a diff to the issue" [L6]. Agent user pages, a Delegate
filter and Insights sliced by delegate give the portfolio view [L1].

**How humans stay in control.** Delegate is not owner: the human stays the assignee [L1]. Admins
install agents, choose "which teams the agent has access to", and agents cannot "sign in to the
app, access admin functionality or manage users" [L1]. Workspace and team **Additional guidance**
steers agents; "team guidance takes priority" [L1]. Loop instructions and every run are
inspectable by "anyone with access" [L7]. The public docs read say nothing on how a human stops a
running session [L8] (UNVERIFIED either way).

**How multiple agents coordinate.** They do not, beyond the board. Nothing read describes
agent-to-agent hand-off, two agents on one issue, or conflict detection [L3], [L8]. Linear Agent
itself runs the coding session; third-party agents (Cursor, Devin, Codex, Factory) each attach to
issues separately. Coordination is humans partitioning work into issues.

**How work links to code, review and release.** The strongest chain on the market: issue →
Code Intelligence context → coding session → draft PR with diff on the issue → Releases moves the
issue when its release completes → agent-written release notes [L5], [L6], [L9]. The link is an
**issue key in a commit message**, not a record of which brief, design or agent produced the change.
Code Intelligence and coding sessions are **GitHub only** in every page read; the release tool is
an open-source CLI that "supports other CI/CD systems" [L9], so Azure Pipelines could feed it, but
no Azure DevOps repository integration was found.

**Enterprise posture.** SOC 2 Type II, ISO 27001:2022, HIPAA BAA, EU or US data residency chosen
at workspace creation, SAML, SCIM, IP restrictions, three months of audit log [L10]. SaaS only.
AI runs on pooled **AI credits** (Loops launched with "$20 per seat" of promotional credit) [L7].
Coding sessions default to "GPT-6 Sol"; admins can pick Claude Opus 5.5 or Sonnet 5 [L6]. No
public page read states model-provider retention terms for coding sessions: **UNVERIFIED**.
Enterprise-managed MCP authorisation with Okta arrived 13 Aug 2026 [L2].

**Where Linear stops.** Its agent is a guest in a sandbox Linear rents, on a board. It has no
brief-to-design phase, no design canvas, no per-user orchestrator, no live file-level awareness
between agents, GitHub only, and pooled credits rather than per-user attributed inference.

## 2. GitHub — Projects, the Copilot cloud agent and Agent HQ

The earlier file covers mission control and Copilot Memory (02-product-prior-art §4). New here:

**How an agent gets work.** Assign the issue to Copilot, Claude, Codex "or all three" from the
Assignees dropdown; each opens a draft PR [G3]. Also `@copilot` on a PR, the agents panel, VS
Code, and "Microsoft Teams, Slack, **Azure Boards**, JIRA, and Linear" integrations [G1]. Copilot
can run "on a schedule or in response to events" [G1]. Dependabot alerts became assignable to
agents on 7 Apr 2026 [G5] (search summary, UNVERIFIED). GitHub is the only vendor found that takes
work **from Azure Boards**; the code must still live on GitHub [G1].

**How progress is shown.** Since 26 Mar 2026 an agent session sits "directly under the assignee in
the sidebar" with four states, **"queued", "working", "waiting for review", "completed"**, and
Projects table and board views get a **"Show agent sessions"** toggle [G2]. Session logs show
research and plan before the PR; "every step happening in a commit" [G1].

**How humans stay in control.** The agent opens a PR; a human merges it. Enterprise admins enable
agents by policy and repositories can opt out [G1]. The **agent control plane** (GA 26 Feb 2026)
lets admins choose which agents and models are available "per team and per repository", set task
policies, and audit agent sessions with an `actor_is_agent` flag and `agent_session.task` start,
finish and failure events [G4] (search summaries, UNVERIFIED in detail). Custom agents are defined
centrally in `.github-private/agents/*.md` [G4] (UNVERIFIED).

**How multiple agents coordinate.** They race. Assigning "all three" yields three competing draft
PRs for a human to pick from [G3]. GitHub's own advice is "be thoughtful about partitioning work"
(02 §4). Copilot Memory shares cited, validated repository facts across agents asynchronously
(02 §4). No live awareness or negotiation.

**How work links to code, review and release.** Native and deep: issue → branch → draft PR →
review → merge → Actions → Releases, all in one product. PR lifecycle metrics for agent PRs come
through the usage metrics APIs [G1]. There is no brief or design artefact upstream of the issue.

**Enterprise posture.** GitHub Enterprise Cloud with SSO, audit log and a data-residency option
(from prior knowledge, not re-read today: UNVERIFIED); the agent
runs in GitHub Actions runners, one repository, one branch, one PR, **59 minutes** maximum [G1].
Billed as Actions minutes plus premium requests under the org's Copilot plan (02 §4). The only
host is GitHub, which rules it out as the whole answer under OD-4 (Azure DevOps and GitHub).

**Where GitHub stops.** Best code-to-release chain and best admin plane, but the agent is a
59-minute contractor per issue. No per-user orchestrator, no cross-owner channel, nothing before
the issue exists, and the three-agent race is parallel waste, not coordination.
